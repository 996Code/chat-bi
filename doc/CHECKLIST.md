# 新产品规划 — 快速检查清单

> 打印出来，逐项打勾。适用于任何软件产品。

---

## 一、产品定义

- [ ] 核心价值用一句话描述（用户视角，包含可衡量指标）
- [ ] 目标用户明确（不是"所有人"）
- [ ] 解决的痛点明确（不是"有比没有好"）
- [ ] 差异化明确（不是"和 XXX 差不多但更好"）

## 二、竞品分析

- [ ] 选了 3-4 个竞品（至少 1 个直接 + 1 个间接 + 1 个反面）
- [ ] 每个竞品深挖了：源码 / Issues / 官方博客 / 用户反馈
- [ ] 每个竞品发现对应了我们自己的一个设计决策
- [ ] 竞品分析不只是功能对比表

## 三、需求定义

- [ ] 需求按功能域分类（AUTH、CORE、UI、API、SEC 等）
- [ ] 每个需求有唯一 ID（如 AUTH-01）
- [ ] 每个需求有优先级（P0/P1/P2/P3）
- [ ] 每个需求有验收标准
- [ ] Out of Scope 明确列出（至少 3 项）
- [ ] 做了至少 3 轮需求补遗

### 基础设施检查清单（最容易遗漏的部分）

- [ ] 密码存储策略（hash 算法 + cost factor）
- [ ] 邮箱验证流程
- [ ] 密码重置流程
- [ ] 登录失败保护（锁定 / 限流）
- [ ] JWT / Session 策略（过期时间、刷新机制）
- [ ] CORS 跨域配置
- [ ] 环境变量清单（.env.example）
- [ ] 日志策略（格式、级别、correlation ID、PII 脱敏）
- [ ] 时区处理方案（如适用）
- [ ] 数据库表设计（DDL + 索引 + 外键）
- [ ] 数据库迁移工具配置
- [ ] Docker / Docker Compose 配置
- [ ] .gitignore
- [ ] CI/CD 流水线
- [ ] 备份与恢复策略
- [ ] 错误处理策略（全局错误中间件）
- [ ] 测试策略（单元 + 集成 + E2E + 覆盖率门控）

### AI/LLM 产品专项检查（如适用）

- [ ] LLM Provider 故障转移（至少 2 个 provider 自动切换）
- [ ] 单次查询成本预算（token 消耗 × 单价 = 美元成本）
- [ ] 内部测试集（每个场景 20-50 个标准 QA 对，CI 自动运行）
- [ ] 语义缓存策略（相似度阈值 + 多层缓存）
- [ ] 多管道模式识别（Indexing / Ask / Follow-up 是否都设计了）
- [ ] 行业基准已验证适用性（而非盲目采信 Spider/BIRD 等公开基准）
- [ ] 输出自纠错机制（AST 校验 / 错误分类 / 重试）
- [ ] 错误类型分布已知（Syntax / Execution / Data Missing / Other）

## 四、追溯映射

- [ ] 每个需求有且仅有一个 Phase 归属
- [ ] checkbox 数量 = 追溯表行数
- [ ] 追溯表中每个 ID 在 checkbox 列表中存在
- [ ] 每个 checkbox 在追溯表中有对应行
- [ ] 覆盖率数字在所有文件中一致

## 五、架构设计

- [ ] 列出了决定产品生死的 3 个技术难题
- [ ] 每个难题有业界最佳实践分析
- [ ] 每个难题有我们的解决方案
- [ ] 每个难题有 Plan B（如果方案不行的话）
- [ ] 画了核心流程图（用户操作 → 系统响应）
- [ ] 标注了每个步骤的耗时
- [ ] 标注了可能失败的点和回退机制
- [ ] 分层架构设计清晰
- [ ] 多管道模式已识别（如适用：Indexing / Ask / Follow-up）

## 六、技术选型

- [ ] 每个技术组件有选型表（候选 / 选择 / 理由）
- [ ] 每个选型有"淘汰了什么 + 为什么"
- [ ] 选型考虑了团队熟悉度
- [ ] v1 选轻量的，不过度设计

## 七、API 设计

- [ ] 所有 API 路径定义清楚（方法 + 路径 + 说明）
- [ ] 每个 API 的请求/响应格式定义清楚
- [ ] 标准错误响应格式统一
- [ ] 分页格式统一
- [ ] 版本号放 URL 路径
- [ ] API 设计在前端开发前完成

## 八、安全设计

- [ ] 威胁模型（列出可能的攻击场景）
- [ ] 多层防护设计（不止一层）
- [ ] 数据库只读账号（如适用）
- [ ] SQL 注入 / XSS / CSRF 防护
- [ ] 敏感数据加密存储
- [ ] 审计日志
- [ ] 多租户隔离（如适用）

## 九、多轮审查

- [ ] 第一轮：自查（逻辑 + 数字 + 引用）
- [ ] 第二轮：独立审查者（不知道规划内容的人/agent）
- [ ] 第三轮：换另一个独立审查者
- [ ] 所有发现的遗漏已修复
- [ ] 一致性检查通过（自动化或手动）

### 一致性检查
- [ ] 需求数量 = 追溯行数
- [ ] 追溯 Phase = ROADMAP Phase
- [ ] 任务总数 = 各 Phase 之和
- [ ] 覆盖率数字在所有文件中一致
- [ ] 无"TODO"、"待定"、"后续补充"占位符

## 十、执行规划

- [ ] 任务按依赖关系分 Wave
- [ ] 每个 Wave 内最大并行度
- [ ] 每个任务有明确的文件归属
- [ ] 每个 Wave 有冒烟测试清单
- [ ] 降级策略（卡住了怎么办）
- [ ] Kill/Pivot 决策点（不达标怎么办）
- [ ] 团队规模和角色明确

## 十一、量化目标

- [ ] 每个量化目标有基线（现在是多少）
- [ ] 每个量化目标有测量方法
- [ ] 每个量化目标有数据来源
- [ ] 没有 marketing claim 和 engineering reality 的矛盾
- [ ] 全链路时间预算已计算（每个步骤耗时 + 最坏情况）
- [ ] 单次操作成本已估算（token 消耗、美元成本）

## 十二、文档集合

- [ ] PROJECT.md（产品概述）
- [ ] REQUIREMENTS.md（需求 + 追溯）
- [ ] ROADMAP.md（Phase + 任务）
- [ ] PLANNING.md（完整技术规划）
- [ ] STATE.md（状态追踪）
- [ ] LESSONS.md / METHODOLOGY.md（经验总结，可选）

---

## 快速自检：如果只能做 5 件事

如果时间紧迫，以下 5 件事是**绝对不能跳过的**：

1. **一句话定义产品**（否则团队不知道在做什么）
2. **需求定义 + Out of Scope**（否则范围无限大）
3. **基础设施清单逐项确认**（否则上线才发现密码没加密）
4. **API 设计**（否则前后端对接反复返工）
5. **至少 1 轮独立审查**（否则一定有遗漏你没看到）
