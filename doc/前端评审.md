## 1. TypeScript Issues

### 1.1 Token refresh race condition in API interceptor
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/api/index.ts`
- **Severity**: must-fix
- **Description**: When multiple requests receive 401 simultaneously, each one independently attempts a token refresh. This causes N concurrent refresh-token calls to the server, which may invalidate the refresh token on the second call.
- **Code**:
  ```ts
  api.interceptors.response.use(
    (response) => response,
    (error) => {
      if (error.response?.status === 401) {
        const refreshToken = localStorage.getItem('refresh_token')
        if (refreshToken) {
          return api.post('/auth/refresh', { refresh_token: refreshToken })
  ```
- **Suggested fix**: Implement a singleton refresh promise. Only the first 401 triggers the refresh; subsequent ones await the same promise.

  ```ts
  let refreshPromise: Promise<void> | null = null

  // Inside interceptor:
  if (error.response?.status === 401) {
    if (!refreshPromise) {
      refreshPromise = doRefreshToken().finally(() => { refreshPromise = null })
    }
    await refreshPromise
    error.config.headers.Authorization = `Bearer ${localStorage.getItem('access_token')}`
    return api.request(error.config)
  }
  ```

### 1.2 `any` type on `error` catch parameters across stores and components

- **Severity**: should-fix
- **Description**: `catch (error: any)` bypasses type safety. While `catch` requires `unknown` in strict mode, using `any` defeats the purpose.
- **Suggested fix**: Use `catch (error: unknown)` and narrow with `if (axios.isAxiosError(error))` before accessing `.response`.

### 1.3 Inconsistent return types in store actions
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/stores/authStore.ts`
- **Severity**: must-fix
- **Description**: `login()` returns `true` on success but a `string` on failure. The return type is inferred as `boolean | string`, making it impossible to type-check callers correctly.
- **Code**:
  ```ts
  async function login(email: string, password: string) {
    // ...
    return true                          // boolean
    // catch:
    return error.response?.data?.detail?.message || '登录失败'  // string
  }
  ```
- **Suggested fix**: Return a discriminated union:
  ```ts
  async function login(...): Promise<{ success: boolean; error?: string }> {
    // on success: return { success: true }
    // on failure: return { success: false, error: '...' }
  }
  ```
  The same pattern exists in `register()` in `authStore.ts`, `create()` and `testConnection()` in `datasourceStore.ts`.

### 1.4 `datasourceStore.remove()` return type inconsistency

### 1.7 JWT token decoding without validation
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/stores/authStore.ts`, lines 24, 40

## 2. Vue3 Composition API Issues

### 2.1 `initFromStorage` called on every route navigation
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/router/index.ts`, line 45
- **Severity**: should-fix
- **Description**: `authStore.initFromStorage()` runs on every `beforeEach` guard. This re-decodes the JWT token on every navigation even when the user is already authenticated. It is also called a second time in `ChatView.vue` `onMounted` (line 185).
- **Suggested fix**: Call `initFromStorage` once in `main.ts` or inside `authStore` initialization, and rely on the `user` ref thereafter. Guard with `if (!user.value)` inside `initFromStorage` (already done, but still redundant).

### 2.2 `currentType` sync via separate watch is fragile
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/components/ChartRenderer.vue`, lines 42-46
- **Severity**: should-fix
- **Description**: `currentType` is a local ref initialized from `props.chartType`, then synced via a watch. This creates a source of truth split. If `props.chartType` changes rapidly, the local ref may be stale during the watch cycle.
- **Suggested fix**: Use `currentType` as a computed or reference `props.chartType` directly in `getOption()` and `renderChart()`.

### 2.3 `deep: true` on array watch is unnecessary and inefficient
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/components/ChartRenderer.vue`, line 146
- **Severity**: should-fix
- **Description**: `watch(() => [props.chartType, props.rows, props.columns], ..., { deep: true })` watches the array reference and deeply traverses every row object. This is expensive for large datasets and unnecessary since only the reference changing matters.
- **Suggested fix**: Remove `deep: true`. The array reference change (new API response) is sufficient to trigger re-render.

### 2.4 FirstUseGuide Teleport may cause hydration/render timing issues
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/components/FirstUseGuide.vue`
- **Severity**: nice-to-have
- **Description**: Using `<Teleport to="body">` is correct in principle, but the component mounts in `ChatView.vue` unconditionally. On route changes or re-renders, the Teleport target may not yet be ready. Also, there is no `deferred` prop to control Teleport timing.
- **Suggested fix**: This is a minor concern for an SPA. The bigger issue is that the guide appears on every mount of `ChatView` if not dismissed (the `localStorage` check prevents re-showing, so this is actually fine).

### 2.5 No error boundary for the application
- **File**: Project-wide
- **Severity**: nice-to-have
- **Description**: There is no `errorCaptured` hook or error boundary component. A runtime error in any child component will crash the entire app with a blank screen.
- **Suggested fix**: Wrap `<router-view>` in `App.vue` with an error boundary component that uses `onErrorCaptured`.

## 3. ECharts Integration

### 3.1 Chart instance not disposed when component unmounts during animation
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/components/ChartRenderer.vue`, lines 155-158
- **Severity**: should-fix
- **Description**: `chart?.dispose()` in `onBeforeUnmount` is correct. However, `chart` is a module-level variable (`let chart: echarts.ECharts | null = null`), not scoped per-component instance. If multiple `ChartRenderer` components exist simultaneously, they share the same `chart` variable, causing dispose/init conflicts.
- **Suggested fix**: Use a `ref<echarts.ECharts | null>` instead of a plain variable, or use `shallowRef` to avoid deep reactivity overhead:
  ```ts
  const chartInstance = shallowRef<echarts.ECharts | null>(null)
  ```

### 3.2 No initial height on ECharts wrapper causes zero-size chart
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/components/ChartRenderer.vue`, line 191-194
- **Severity**: must-fix
- **Description**: `.echarts-wrapper` has `height: 320px` set via CSS, which is correct. However, if the component is rendered inside a container with `display: none` or flex without proper sizing, `echarts.init` may create a zero-size canvas. ECharts v5 handles this better but it is still worth guarding.
- **Suggested fix**: Add a check in `renderChart()`:
  ```ts
  if (!chartRef.value || chartRef.value.offsetWidth === 0) return
  ```
  Or use `chart.resize()` after a `nextTick`.

### 3.3 Empty options fallthrough
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/components/ChartRenderer.vue`, line 116
- **Severity**: should-fix
- **Description**: If columns < 2 or chart type is unrecognized, `getOption()` returns `{}`. Then `renderChart()` checks `Object.keys(option).length > 0` before calling `setOption`. This means a previous chart may remain visible when new data cannot be charted.
- **Suggested fix**: Show an explicit "no chart data" message or fall back to the table view.

### 3.4 Resize listener not debounced
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/components/ChartRenderer.vue`, line 152
- **Severity**: nice-to-have
- **Description**: `window.addEventListener('resize', handleResize)` fires on every resize event. Debouncing is recommended for performance.
- **Suggested fix**: Use `lodash/debounce` or a simple debounce utility.

## 4. API Integration

### 4.1 No response error for non-401 HTTP errors
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/api/index.ts`
- **Severity**: must-fix
- **Description**: The response interceptor only handles 401. All other HTTP errors (500, 404, 403, 429, network errors) pass through as rejected promises with no centralized handling or logging. Each caller must individually handle errors.
- **Suggested fix**: Add a generic error handler that logs the error and, optionally, shows a global `ElMessage.error` for server errors.

### 4.2 Token refresh URL may hit the wrong base URL
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/api/index.ts`, line 29
- **Severity**: should-fix
- **Description**: Inside the interceptor, `api.post('/auth/refresh', ...)` uses the same axios instance which has `baseURL: '/api/v1'`. So the actual URL is `/api/v1/auth/refresh`. If the refresh endpoint lives at `/api/v1/auth/refresh`, this is correct. But if the refresh endpoint is at a different path (e.g., `/api/auth/refresh`), this will fail. Verify with the backend.

### 4.3 Axios config is re-serialized incorrectly on retry
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/api/index.ts`, line 35
- **Severity**: must-fix
- **Description**: `api.request(error.config)` reuses the internal Axios config object which may contain properties that `request()` does not expect (like `baseURL`, `transformRequest`, etc.). The standard pattern is to use `axios(error.config)` (the raw axios function) or `api.request({ ...error.config })`.
- **Suggested fix**:
  ```ts
  return axios(error.config)
  ```
  (import `axios` directly) or strip non-request properties from `error.config`.

### 4.4 `api` used in ChatView without import
- **File**: `/Users/xiaotaotao/cyble-code/chat-bi/frontend/src/views/ChatView.vue`, line 165
- **Severity**: must-fix
- **Description**: `submitFeedback` calls `api.post('/feedback', ...)` but `api` is never imported in this file. This is a runtime error that will crash when feedback is submitted.
- **Code**:
  ```ts
  async function submitFeedback(msg: any, rating: 'up' | 'down') {
    try {
      await api.post('/feedback', {  // <-- api is not imported!
  ```
- **Suggested fix**: Add `import api from '@/api'` at the top of the script.

### 4.5 No request deduplication
- **File**: Project-wide
- **Severity**: nice-to-have
- **Description**: If the user clicks "发送" twice rapidly (despite the disabled button), or switches datasources and triggers multiple requests, there is no request cancellation. AbortController should be used.
- **Suggested fix**: Store an `AbortController` and call `.abort()` before starting a new request.
