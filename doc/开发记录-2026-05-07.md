## 关键修复和优化

### 1. 环境变量统一 — 单文件多环境

**问题：** 环境变量分散在 `deploy/.env`、`backend/.env`、`backend/.env.home`、`backend/.env.office`、`frontend/.env` 多处，修改时容易遗漏或不同步。

**解决方案：**
- 根目录创建 `.env` 作为唯一配置文件
- `.env.home` 和 `.env.office` 作为环境模板
- 后端 pydantic-settings 直接读根 `.env`（`BASE_DIR` 已指向项目根）
- 前端 Vite 通过 `envDir: resolve(__dirname, '..')` 读根 `.env`
- `docker-compose.yml` 和 `deploy.sh` 都指向根 `.env`
- Docker 构建时将根 `.env` COPY 到前端构建上下文

### 2. Pydantic `extra="forbid"` 冲突

**问题：** 根 `.env` 包含 `DEPLOY_*`（docker-compose 专用）和 `VITE_*`（前端专用）变量，pydantic Settings 的 `extra="forbid"` 会拒绝未知字段。

**解决方案：** 在 Settings 模型中新增对应可选字段，后端忽略但能识别：
```python
chatbi_port: int = 28080
deploy_mysql_port: int = 3306
deploy_mysql_root_password: str = ""
deploy_mysql_database: str = "chatbi"
deploy_redis_port: int = 6379
vite_base_path: str = "/chat-bi/"
vite_api_prefix: str = "/chat-bi/api/v1"
```

### 3. Vite envDir 配置

**问题：** Vite 默认从当前目录（frontend/）读取 `.env`，不在项目根。

**解决方案：** `vite.config.ts` 设置 `envDir: resolve(__dirname, '..')` 指向项目根。

## 踩坑记录

### Dockerfile 构建时前端找不到 .env

**问题：** Docker 构建时前端在容器内的 `/app/frontend` 工作，Vite envDir 指向 `/app` 但根 `.env` 不在构建上下文中。

**解决方案：** Dockerfile 中 `COPY .env /app/.env` 在 frontend-builder 阶段将根 `.env` 复制到正确位置。

### symlink vs 文件

**问题：** 后端和前端目录仍保留 `.env` 文件，但内容已迁移到根目录。

**解决方案：** 将 `backend/.env*` 和 `frontend/.env` 替换为符号链接指向根目录对应文件，保持 IDE 和工具的兼容性。

## 关键修复和优化

### 1. 后台查询补全执行流程（Pipeline Trace）

**问题：** 后台查询（`POST /query/async`）前端只显示 2 个扁平步骤（"后台查询 → 执行查询"），缺少意图识别、Schema 选择、SQL 生成、图表推断等完整流程。SSE 查询有 6-8 个详细步骤。

**根因：** `_run_async_query` 用 `graph.ainvoke()` 只拿到最终结果，中间步骤全部丢失。

**解决方案：**
- 新建 `pipeline_executor.py` 共享异步生成器，逐步产出结构化事件 dict
- SSE 路径（`stream_query`）和后台路径（`_run_async_query`）共用同一管线
- 后台查询收集所有事件到 `pipeline_trace`（JSON array），存入数据库
- 前端轮询完成后可选重放 `pipeline_trace` 通过 `handleSSEEvent` 构建完整 pipeline

**产出事件序列：** cache → intent → semantics → sql → data → chart → complete/error

### 2. 自动数据库迁移

**问题：** `Base.metadata.create_all` 只创建新表，不会对已有表执行 ALTER TABLE。新增的 intent/pipeline_trace 列在已部署的 MySQL 上不存在，导致 `Unknown column 'intent' in 'field list'` 500 错误。

**解决方案：** `main.py` lifespan 启动时执行 `SHOW COLUMNS` 检测，缺失则 `ALTER TABLE ADD COLUMN`。SQLite 自动支持，MySQL/PG 需动态迁移。

### 3. 缓存策略优化

**问题：** 每次启动缓存未清空，数据模型刷新后查询缓存也未清除。

**解决方案：**
- `main.py` lifespan 启动时调用 `cache_clear_all()` 清除所有 query/semantic/cache_index 缓存
- `data_model.py` 全量/增量同步完成后调用 `cache_clear_datasource(ds_id)` 清除对应数据源缓存
- 使用 Redis set 按数据源索引所有缓存 key，实现精确清除（scan + delete 每个 key）

### 4. 后台查询实时进度

**问题：** 后台查询运行中前端只显示一个 loading 状态，没有阶段性进度。

**解决方案：**
- `_run_async_query` 每执行一步就将当前 pipeline_trace 存入 Redis `async_trace:{task_id}`
- `get_async_query_status` 在 status=running 时从 Redis 读取中间步骤返回
- 前端 `pollAsyncTask` 轮询时重建 `pipelineSteps`，实时显示进行中/已完成步骤

### 5. _run_async_query 变量预初始化

**问题：** 非 DataQuery 路径（如 DashboardUpdate）进入 event loop 前，`sql`、`columns`、`rows` 等变量未定义，导致 UnboundLocalError。

**解决方案：** async for loop 前设置默认值：
```python
sql = ""
columns = []
rows = []
error = None
final_success = False
chart_type = None
```

### 6. TypeScript 编译错误

**问题：** `replayMsg.pipelineSteps` 可能 undefined，TS strict null check 报错。

**解决方案：** 使用 `?.` 可选链和 `!` 非空断言：
```typescript
(replayMsg.pipelineSteps?.length || 0)
replayMsg.pipelineSteps![stepIdx]
```

### 7. Vue 3 响应式更新 + Decimal 序列化

**问题：** 直接修改 `msg.pipelineSteps[idx].status` Vue 不检测变化；Decimal 类型无法 JSON 序列化。

**解决方案：**
- 替换整个 pipelineSteps 数组对象（`msg.pipelineSteps = [...msg.pipelineSteps]`）
- `json.dumps` 添加 `default=str` 处理 Decimal

## 踩坑记录

### create_all 不添加新列

`SQLAlchemy create_all` 只会创建不存在的表，不会对已有表执行 ALTER。已部署的数据库必须通过迁移脚本（Alembic）或动态检测添加新列。本次采用轻量级动态迁移（SHOW COLUMNS + ALTER TABLE）。

### Redis 存中间步骤的 key 设计

后台查询中间步骤存 Redis key `async_trace:{task_id}`，TTL 设为 1 小时。task_id 本身就是唯一标识，无需额外前缀。

### Vue 3 ref 数组元素属性变更不触发响应式

直接修改 `arr[i].prop = value` 不会触发 Vue 响应式更新。必须替换整个数组或该元素对象：`arr.value = [...arr.value]` 或 `arr.value[i] = { ...arr.value[i], prop: newValue }`。
