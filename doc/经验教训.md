# 新产品规划方法论 — ChatBI 经验总结

> **规划的本质：降低失败方式的搜索空间。**
> 不是"预测未来会发生什么"，而是"提前想清楚所有可能失败的方式，然后逐一排除"。

**基于项目**: ChatBI（自然语言 → SQL → 图表 SaaS 产品）
**规划周期**: 需求定义 → 竞品分析 → 架构设计 → 多轮审查 → 执行规划
**文档数量**: 5 个规划文件（PLANNING.md 2890 行 / PROJECT.md / REQUIREMENTS.md 256 行 / ROADMAP.md / STATE.md）
**需求数量**: 88 个 v1 需求 → 经过 5 轮审查从 42 补到 88，0 遗漏

---

## 第一部分：规划的全流程（8 步）

### 第一步：一句话定义产品

> "让不会 SQL 的人也能自助完成数据查询和可视化，3 秒内得到图表答案。"

**关键认知**：核心价值必须用**用户视角**表述（"用户 3 秒得到答案"），不是技术视角（"AI 生成 SQL 的工具"）。如果一句话说不清楚产品要解决什么问题，说明还没想明白。

### 第二步：竞品分析（先理解别人做过什么、踩过什么坑）

ChatBI 深挖了 4 个竞品（WrenAI、Vanna AI、DB-GPT、SQLChat），每个都看了源码、官方博客、Issues。

**最有价值的发现不是"竞品有什么功能"，而是"竞品踩过什么坑"**：

| 竞品经验 | 转化为我们的决策 |
|---------|----------------|
| WrenAI 准确率提升 40% 靠的是语义层，不是换更强的 LLM | 核心设计：MDL 风格语义层先行 |
| 29%-49% 的 Text-to-SQL 错误来自 Schema Linking 失败 | 重点攻克：RAG 三层索引 + Column Pruning |
| WrenAI 早期用 LangChain Agent → 失控 | 决策：选 LangGraph 确定性工作流 |
| LLM 需要的不是更多数据，而是更好的上下文 | 核心理念：Context Engineering |

**WrenAI 深挖的 5 个具体陷阱**（这些是最有价值的"借别人的失败"）：

| WrenAI 陷阱 | 具体表现 | 我们的对策 |
|-------------|---------|-----------|
| Schema 幻觉 | LLM 编造不存在的表/列 | RAG 三层索引 + Schema Linking 验证 |
| Agent 失控 | LangChain 自动生成的步骤不可预测 | 确定性工作流（LangGraph），每步有校验 |
| 无多轮对话 | 上下文丢失，追问无法关联 | 三管道架构：Indexing / Ask / Follow-up |
| 同步架构崩溃 | 长查询阻塞，并发上不去 | 异步 + SSE 流式输出 |
| 无记忆机制 | 相同查询每次重新生成 | 三层缓存（语义缓存阈值 >0.95） |

**教训**：竞品分析不是写报告给人看的，是**给自己避雷用的**。每一个竞品优势/坑，都要对应一个我们自己的设计决策。

### 第三步：需求定义（分类 + 编号 + 优先级）

12 个分类，88 个需求，每个有唯一 ID（如 AUTH-01），优先级分 P0-P3。

**关键教训**：
- 需求定义不是一次性写完的。一开始 42 个，5 轮审查补到 88 个。**"显性需求"和"隐性基础设施需求"的比例大约是 1:1。**
- 遗漏的往往是不起眼的"基础设施"：密码策略、CORS、邮箱验证、环境变量、日志格式、时区处理。
- Out of Scope 同样重要。明确说"不做"什么，和明确说"做"什么一样关键。

### 第四步：需求到 Phase 的追溯映射

**规则**：每个需求有且仅有一个 Phase 归属。

**检查方法**：`checkbox 数量 = 追溯表行数 = 各 Phase 需求之和`

ChatBI 在这点上反复检查了 4 轮才完全一致。

### 第五步：架构设计（先解决最难的）

把最难的东西列出来，问自己："如果这个做不成，产品还有价值吗？" 如果答案是"没有"，这就是第一优先级的设计重点。

### 第六步：技术栈选型

每个选型必须有"淘汰了什么 + 为什么"的对比。不要只说"选了 A"，要说"选了 A 而不是 B，因为..."。

### 第七步：多轮独立审查

ChatBI 做了 5 轮审查，每轮都有新发现：

| 轮次 | 审查者 | 发现遗漏数 | 主要发现 |
|------|--------|----------|---------|
| 1 | 主 agent | 14 | 密码策略、邮箱验证、环境变量、前端路由、时区、日志、测试、DB 表设计 |
| 2 | 独立 agent | 5 | 覆盖数字错误、反馈表缺索引、邮箱验证未设计、优先级矛盾 |
| 3 | 双 agent 并行 | 2 | PERF-05/06 在追溯表缺失、feedback 缺 query_id 索引 |
| 4 | 审计 agent | 0 | 全部一致 |
| 5 | 总结 agent | 0 | 全部一致 |

**核心教训**：自己写的东西永远看不到自己的盲点。每次审查都发现了真正的遗漏，没有一轮是"白跑"的。

### 第八步：执行规划（并行化）

- 任务按依赖关系分 Wave（A1→A2→B1→B2→C）
- 每个 Wave 内 3 个 agent 并行
- 每个 agent 有明确的文件归属（防冲突）
- Wave 之间有冒烟测试关卡
- 降级策略：某个 agent 卡住 15 分钟则简化需求先跑通

## 第二部分：10 条深层认知

### 认知 1：规划的目标不是预测正确，而是排除失败

> **你写文档时的注意力集中在"什么是对的"上，但失败往往来自"什么是漏的"。这两种思维模式几乎不可能由同一人在同一时间完成。**

所以规划的真正价值不是写出"对的"东西，而是通过反复审查找出"漏的"东西。写只是 20% 的工作，查漏才是 80%。

**ChatBI 的具体失败模式**：
- **BI 经典陷阱**：Fan Trap（一对多对多产生笛卡尔积）和 Chasm Trap（多对一对多导致数据重复）——LLM 不懂这些，必须在架构层排除
- **Text-to-SQL 错误分布**：Syntax 错误 37%（SQL 语法不对）、Execution 错误 29%（表/列不存在）、Data Missing 21%（数据缺失）、Other 13%（逻辑错误）→ 每种需要不同的纠正策略
- **自纠错回路设计**：SQL 生成 → AST 校验 → 执行 → 错误分类 → 重试（最多 3 轮），每类错误有专门的纠正 prompt

### 认知 2：每个"显性需求"背后都藏着一个"隐性基础设施需求"

> **人们定义产品时天然倾向于关注"用户能看到的"部分，而忽略"用户看不到但系统离不开的"部分。这两者的比例大约是 1:1。**

这不是疏忽，是认知偏差。大脑天然对"显性"的东西敏感，对"隐性"的东西迟钝。解决方案不是"下次注意"，而是**在需求定义阶段就引入"基础设施检查清单"作为外部认知工具**。

**最常被遗漏的基础设施**：

| 遗漏项 | 为什么容易被遗漏 | 后果 |
|--------|----------------|------|
| 密码 hash 策略 | 默认"密码当然要加密" | 安全审计不过 |
| 邮箱验证流程 | 觉得"注册了就行" | 垃圾账号泛滥 |
| 密码重置 | 觉得"先做了登录再说" | 用户无法自助使用 |
| CORS 跨域 | 前后端分离必做，但没人提 | 前端调不通 API |
| 环境变量清单 | 觉得"写了代码自然知道" | 部署时一脸懵 |
| 日志格式/级别 | 觉得"有日志就行" | 排查问题时找不到关键信息 |
| 时区处理 | 觉得"UTC 就行了" | BI 产品中"上个月"算错月份 |
| 测试策略 | 觉得"写了代码再测" | 没有测试门控，代码质量失控 |

### 认知 3：借别人的失败比自己踩坑 ROI 高 100 倍

> **你自己踩一个坑的成本是：发现问题的时间 + 解决问题的时间 + 已写代码的废弃成本。借别人的坑的成本是：读一篇博客的时间。**

但大多数人做竞品分析只停留在功能对比表，不看源码、不看 Issues、不看官方博客。这是把竞品分析当成了"交差"而不是"避险"。

**WrenAI 的 8 个核心优势**（不是功能列表，而是设计模式的提炼）：
- 语义层 2.0（MDL：模型/关系/指标声明式定义，LLM 只需读结构不需猜）
- RAG 三层（Table → Column → Value，不是全量 dump schema）
- Self-healing（SQL 失败自动纠错，不是直接报错误）
- Feedback loop（用户反馈直接回流到 Schema Linking 权重）
- 三管道架构（Indexing 预计算 / Ask 首次查询 / Follow-up 上下文继承）
- 三层缓存（Exact → Semantic → Intent，避免重复 LLM 调用）
- 意图识别（DataQuery vs Other，不是所有输入都走 SQL 生成）
- 声明式图表（LLM 输出 chart_spec JSON，前端渲染，不是 LLM 生成图片）

### 认知 4：文档一致性不是洁癖，是信任的基础

> **文档之间的不一致不是"小错误"——它是整个团队信任体系的裂缝。当开发者发现"需求文档说有 88 个但状态文档说 83 个"时，他下一个念头不是"哦差了 5 个"，而是"这份文档到底靠不靠谱？"**

一致性检查不是整理文件的洁癖行为，而是维护团队对规划的信任。一旦信任破裂，规划就变成了"仅供参考"的废纸。

### 认知 5：任何不可精确测量的目标都是愿望，不是规划

ChatBI 的核心价值是"3 秒"，但工程规划中全链路最坏情况 15-20 秒。Phase 2 目标是"准确率 > 70%"，但没有定义当前基线。

> **marketing claim 和 engineering reality 之间的 gap，是产品规划中最危险的未爆炸弹。不是因为它做不到，而是因为它没有被正确定义——是 P50 还是 P95？缓存命中算不算？**

"从 X 提升到 Y" 和 "达到 Y" 是完全不同的两件事。没有基线的目标只是一个愿望，不是规划。

**ChatBI 的全链路时间预算**：Intent(200ms) → Schema(1s) → SQL(3s) → AST(100ms) → Cache(50ms) → Execute(5s) → Chart(500ms) → SSE 流式输出。最坏情况 ~15s，不是 3s。

**成本量化**：单次查询约 $0.048（Sonnet），1000 次/天 = $48/天 = $1,440/月。优化手段：语义缓存 30-50% 命中、Column Prune 节省 40-60% token、模型路由节省 31-80%。不做成本规划 = 预算失控。

**行业基准的陷阱**：Spider/BIRD/Spider 2.0 标注错误率 52.8%-62.8%。公开基准对生产环境参考价值有限——必须构建内部测试集（每个数据源 20-50 个标准 QA 对），每次代码变更自动运行，测量执行准确率。

### 认知 6：自己永远看不到自己的盲点

> **写文档的人的注意力已经"锁定"在当前的理解框架里了。即使他反复读自己的文档，也只能在已有的理解范围内发现问题。真正有价值的审查来自"不知道你在想什么"的人。**

这解释了为什么"自查"只能发现格式和数字错误，而独立审查才能发现结构性遗漏。

**ChatBI 盲点典型案例**：
- **LLM Provider 故障转移**：一开始只配了单一 LLM，第 2 轮审查才意识到需要 OpenAI/Anthropic/Dashscope 自动切换（一个挂了就切另一个）
- **三管道模式**：一开始只设计了"用户提问 → 系统回答"一个流程，第 3 轮才发现实际有三种管道：Indexing（预计算）、Ask（首次查询）、Follow-up（上下文继承追问），每种管道的工作流完全不同

### 认知 7："不做"定义了产品的边界

> **不做什么是产品规划的"负面空间"——它定义了产品的边界。没有边界的产品注定会范围蔓延，因为"一切都有道理做"。决定"不做"什么，是产品决策中唯一能真正保护团队注意力的行为。**

**ChatBI v1 明确不做的**：
- 不做多数据源 JOIN 查询（跨库关联太复杂，v2 再做）
- 不做实时数据同步（定时扫描即可）
- 不做自定义 SQL 编辑器（面向不会 SQL 的用户）
- 不做移动端适配（B 端产品，桌面优先）
- 不做 AI 自动生成看板（先跑通单次查询）

### 认知 8：规划阶段的"慢"是为了执行阶段的"快"

ChatBI 规划阶段投入约 12 小时，换来的是：执行阶段开发者拿到可直接开工的文档、避免了至少 15+ 个执行阶段才会发现的遗漏、避免了前后端对接时的反复沟通。

> **规划阶段的每个小时，大约能节省执行阶段 3-5 小时的返工。但更关键的是，规划避免的那些"写到一半发现方案错了"的重构，其代价不是按小时算的，是按周算的。**

### 认知 9：核心难题必须有 Plan B

对每个"决定产品生死"的技术难题，不能假设"一定能成"。必须定义：如果这个方案失败了，什么时候 Kill？什么时候 Pivot？Plan B 是什么？

### 认知 10：规划文档的"最小可用信息量"

> **规划文档不是越长越好，也不是越短越好。它的"最小可用信息量"是：一个完全不了解这个项目的开发者，读完之后能直接开始写代码，而不需要向任何人提问。**

如果开发者还需要问"密码怎么存？"、"环境变量有哪些？"、"API 错误返回什么格式？"——说明规划还没到"可执行"的程度。

**"最小可用信息量"的测试**：把文档给一个完全不了解这个项目的开发者，看他多久能开始写第一个 PR。如果还需要问超过 3 个问题，说明文档还不够。

## 第六部分：从 0 到 1 执行阶段的经验总结

> **规划只是开始，执行才是检验真理的地方。以下每一条都是从实际开发和测试中踩出来的教训。**

### 一、环境配置集中化

**教训**：一开始超时、限流、LLM 参数等硬编码在 13 个文件里，改一个值要翻多个文件。

**做法**：所有配置集中到 `config.py`，通过环境变量控制。`.env.example` 同步更新。新增约 30 个配置项。

**检查项**：
- [ ] 所有魔法数字（超时、阈值、默认值）是否都提取到配置类？
- [ ] `.env.example` 是否包含所有必填/选填变量？
- [ ] 默认值是否在无 `.env` 时也能启动？

### 二、测试必须跑真实数据，不能用假数据库

**教训**：seed 数据里写了 `ecommerce`、`demo_db` 等不存在的数据库，导致数据源连接测试全部失败。看起来"功能正常"，但实际全是 CONNECTION_FAILED。

**做法**：数据源必须指向真实可连的数据库。测试前先用 `SHOW DATABASES` 确认可用库，seed 数据用真实存在的库名和账号。

**检查项**：
- [ ] 所有 seed 数据源是否能实际 `SELECT 1` 成功？
- [ ] 元数据配置（metadata_configs）的 schema 是否来自真实扫描或真实结构？
- [ ] 测试用户能否真实登录（密码 hash 正确、邮箱验证状态正确）？

### 三、JWT token 必须包含所有权限判断需要的字段

**教训**：JWT 里没有 `role` 字段，导致 `/audit` 接口的 admin 检查永远失败。即使是 admin 也 403。这个 bug 在单元测试里没被发现（因为测试不验证角色逻辑）。

**做法**：登录创建 token 时，把所有后续鉴权需要的字段都写进去：`user_id`、`email`、`tenant_id`、`role`。刷新 token 时同样。

**检查项**：
- [ ] JWT payload 是否包含所有 downstream 鉴权需要的字段？
- [ ] 刷新 token 是否也包含完整字段？
- [ ] 权限判断是否基于 JWT 字段而不是重新查 DB（性能和一致性）？

### 四、异步 ORM 的 merge vs add

**教训**：SQLAlchemy async session 的 `merge()` 返回 coroutine，需要 `await`。而 `add()` 是同步方法，直接调用即可。seed 脚本用 `merge()` 但没 await，导致数据根本没写入。

**做法**：批量插入用 `session.add()` 然后 `commit()`。如果需要用 merge（upsert），必须 `await session.merge(obj)`。

### 五、测试隔离：单元测试用 SQLite，不影响真实数据库

**做法**：`conftest.py` 在导入 app 之前设置 `os.environ["DATABASE_URL"]` 为 SQLite，确保测试不污染开发数据库。每个测试自动建表/删表。

### 六、API 冒烟测试必须覆盖所有核心端点

**教训**：不能只看 health 和 login。每个模块都要测：
- auth: 注册、登录、刷新、锁定、未验证拒绝
- datasources: 列表、创建、测试连接、删除
- queries: 列表、保存、重跑
- feedback: 列表、提交
- audit: admin 可访问、非 admin 拒绝
- export/csv: 正常导出
- conversations: 列表

### 七、测试套件执行规范

**每次代码变更后的测试流程**：
1. `.venv/bin/python -m pytest tests/ -x -q` — 全量测试，确保 190 passed
2. 启动后端 `uvicorn app.main:app` — 确认启动无报错
3. 逐个测试关键 API（至少 login、datasources list、query POST）
4. 验证 MySQL 数据完整性（表行数与预期一致）
5. 数据源连接测试必须返回 `success: true`

### 八、seed 脚本是可复用的基础设施

**做法**：`seed.py` 必须支持重复运行（truncate + insert），每次都能得到一致的数据。UUID 固定（不用随机生成），方便测试引用。

### 九、前端 500 排查清单

当前端说"所有接口都 500"时：
1. 先 `curl health` 确认后端活着
2. 检查前端 proxy target 是否指向正确端口（通常是 8000）
3. 确认没有多个 uvicorn 进程占着端口（`lsof -ti :8000`）
4. 看后端日志里有没有实际收到请求
5. 检查 CORS 配置是否允许前端域名
