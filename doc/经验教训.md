# 新产品规划方法论 — ChatBI 经验总结

> **规划的本质：降低失败方式的搜索空间。**
> 不是"预测未来会发生什么"，而是"提前想清楚所有可能失败的方式，然后逐一排除"。

**基于项目**: ChatBI（自然语言 → SQL → 图表 SaaS 产品）
**规划周期**: 需求定义 → 竞品分析 → 架构设计 → 多轮审查 → 执行规划
**文档数量**: 5 个规划文件（PLANNING.md 2890 行 / PROJECT.md / REQUIREMENTS.md 256 行 / ROADMAP.md / STATE.md）
**需求数量**: 88 个 v1 需求 → 经过 5 轮审查从 42 补到 88，0 遗漏

---

## 第一部分：规划的全流程（8 步）

### 第一步：一句话定义产品

> "让不会 SQL 的人也能自助完成数据查询和可视化，3 秒内得到图表答案。"

**关键认知**：核心价值必须用**用户视角**表述（"用户 3 秒得到答案"），不是技术视角（"AI 生成 SQL 的工具"）。如果一句话说不清楚产品要解决什么问题，说明还没想明白。

### 第二步：竞品分析（先理解别人做过什么、踩过什么坑）

ChatBI 深挖了 4 个竞品（WrenAI、Vanna AI、DB-GPT、SQLChat），每个都看了源码、官方博客、Issues。

**最有价值的发现不是"竞品有什么功能"，而是"竞品踩过什么坑"**：

| 竞品经验 | 转化为我们的决策 |
|---------|----------------|
| WrenAI 准确率提升 40% 靠的是语义层，不是换更强的 LLM | 核心设计：MDL 风格语义层先行 |
| 29%-49% 的 Text-to-SQL 错误来自 Schema Linking 失败 | 重点攻克：RAG 三层索引 + Column Pruning |
| WrenAI 早期用 LangChain Agent → 失控 | 决策：选 LangGraph 确定性工作流 |
| LLM 需要的不是更多数据，而是更好的上下文 | 核心理念：Context Engineering |

**WrenAI 深挖的 5 个具体陷阱**（这些是最有价值的"借别人的失败"）：

| WrenAI 陷阱 | 具体表现 | 我们的对策 |
|-------------|---------|-----------|
| Schema 幻觉 | LLM 编造不存在的表/列 | RAG 三层索引 + Schema Linking 验证 |
| Agent 失控 | LangChain 自动生成的步骤不可预测 | 确定性工作流（LangGraph），每步有校验 |
| 无多轮对话 | 上下文丢失，追问无法关联 | 三管道架构：Indexing / Ask / Follow-up |
| 同步架构崩溃 | 长查询阻塞，并发上不去 | 异步 + SSE 流式输出 |
| 无记忆机制 | 相同查询每次重新生成 | 三层缓存（语义缓存阈值 >0.95） |

**教训**：竞品分析不是写报告给人看的，是**给自己避雷用的**。每一个竞品优势/坑，都要对应一个我们自己的设计决策。

### 第三步：需求定义（分类 + 编号 + 优先级）

12 个分类，88 个需求，每个有唯一 ID（如 AUTH-01），优先级分 P0-P3。

**关键教训**：
- 需求定义不是一次性写完的。一开始 42 个，5 轮审查补到 88 个。**"显性需求"和"隐性基础设施需求"的比例大约是 1:1。**
- 遗漏的往往是不起眼的"基础设施"：密码策略、CORS、邮箱验证、环境变量、日志格式、时区处理。
- Out of Scope 同样重要。明确说"不做"什么，和明确说"做"什么一样关键。

### 第四步：需求到 Phase 的追溯映射

**规则**：每个需求有且仅有一个 Phase 归属。

**检查方法**：`checkbox 数量 = 追溯表行数 = 各 Phase 需求之和`

ChatBI 在这点上反复检查了 4 轮才完全一致。

### 第五步：架构设计（先解决最难的）

把最难的东西列出来，问自己："如果这个做不成，产品还有价值吗？" 如果答案是"没有"，这就是第一优先级的设计重点。

### 第六步：技术栈选型

每个选型必须有"淘汰了什么 + 为什么"的对比。不要只说"选了 A"，要说"选了 A 而不是 B，因为..."。

### 第七步：多轮独立审查

ChatBI 做了 5 轮审查，每轮都有新发现：

| 轮次 | 审查者 | 发现遗漏数 | 主要发现 |
|------|--------|----------|---------|
| 1 | 主 agent | 14 | 密码策略、邮箱验证、环境变量、前端路由、时区、日志、测试、DB 表设计 |
| 2 | 独立 agent | 5 | 覆盖数字错误、反馈表缺索引、邮箱验证未设计、优先级矛盾 |
| 3 | 双 agent 并行 | 2 | PERF-05/06 在追溯表缺失、feedback 缺 query_id 索引 |
| 4 | 审计 agent | 0 | 全部一致 |
| 5 | 总结 agent | 0 | 全部一致 |

**核心教训**：自己写的东西永远看不到自己的盲点。每次审查都发现了真正的遗漏，没有一轮是"白跑"的。

### 第八步：执行规划（并行化）

- 任务按依赖关系分 Wave（A1→A2→B1→B2→C）
- 每个 Wave 内 3 个 agent 并行
- 每个 agent 有明确的文件归属（防冲突）
- Wave 之间有冒烟测试关卡
- 降级策略：某个 agent 卡住 15 分钟则简化需求先跑通

## 第二部分：10 条深层认知

### 认知 1：规划的目标不是预测正确，而是排除失败

> **你写文档时的注意力集中在"什么是对的"上，但失败往往来自"什么是漏的"。这两种思维模式几乎不可能由同一人在同一时间完成。**

所以规划的真正价值不是写出"对的"东西，而是通过反复审查找出"漏的"东西。写只是 20% 的工作，查漏才是 80%。

**ChatBI 的具体失败模式**：
- **BI 经典陷阱**：Fan Trap（一对多对多产生笛卡尔积）和 Chasm Trap（多对一对多导致数据重复）——LLM 不懂这些，必须在架构层排除
- **Text-to-SQL 错误分布**：Syntax 错误 37%（SQL 语法不对）、Execution 错误 29%（表/列不存在）、Data Missing 21%（数据缺失）、Other 13%（逻辑错误）→ 每种需要不同的纠正策略
- **自纠错回路设计**：SQL 生成 → AST 校验 → 执行 → 错误分类 → 重试（最多 3 轮），每类错误有专门的纠正 prompt

### 认知 2：每个"显性需求"背后都藏着一个"隐性基础设施需求"

> **人们定义产品时天然倾向于关注"用户能看到的"部分，而忽略"用户看不到但系统离不开的"部分。这两者的比例大约是 1:1。**

这不是疏忽，是认知偏差。大脑天然对"显性"的东西敏感，对"隐性"的东西迟钝。解决方案不是"下次注意"，而是**在需求定义阶段就引入"基础设施检查清单"作为外部认知工具**。

**最常被遗漏的基础设施**：

| 遗漏项 | 为什么容易被遗漏 | 后果 |
|--------|----------------|------|
| 密码 hash 策略 | 默认"密码当然要加密" | 安全审计不过 |
| 邮箱验证流程 | 觉得"注册了就行" | 垃圾账号泛滥 |
| 密码重置 | 觉得"先做了登录再说" | 用户无法自助使用 |
| CORS 跨域 | 前后端分离必做，但没人提 | 前端调不通 API |
| 环境变量清单 | 觉得"写了代码自然知道" | 部署时一脸懵 |
| 日志格式/级别 | 觉得"有日志就行" | 排查问题时找不到关键信息 |
| 时区处理 | 觉得"UTC 就行了" | BI 产品中"上个月"算错月份 |
| 测试策略 | 觉得"写了代码再测" | 没有测试门控，代码质量失控 |

### 认知 3：借别人的失败比自己踩坑 ROI 高 100 倍

> **你自己踩一个坑的成本是：发现问题的时间 + 解决问题的时间 + 已写代码的废弃成本。借别人的坑的成本是：读一篇博客的时间。**

但大多数人做竞品分析只停留在功能对比表，不看源码、不看 Issues、不看官方博客。这是把竞品分析当成了"交差"而不是"避险"。

**WrenAI 的 8 个核心优势**（不是功能列表，而是设计模式的提炼）：
- 语义层 2.0（MDL：模型/关系/指标声明式定义，LLM 只需读结构不需猜）
- LLM 两步 Schema 选择（先选表再选字段，替代 RAG 关键词检索）
- Self-healing（SQL 失败自动纠错，不是直接报错误）
- Feedback loop（用户反馈直接回流到 Schema Linking 权重）
- 三管道架构（Indexing 预计算 / Ask 首次查询 / Follow-up 上下文继承）
- 三层缓存（Exact → Semantic → Intent，避免重复 LLM 调用）
- 意图识别（DataQuery vs Other，不是所有输入都走 SQL 生成）
- 声明式图表（LLM 输出 chart_spec JSON，前端渲染，不是 LLM 生成图片）

### 认知 4：文档一致性不是洁癖，是信任的基础

> **文档之间的不一致不是"小错误"——它是整个团队信任体系的裂缝。当开发者发现"需求文档说有 88 个但状态文档说 83 个"时，他下一个念头不是"哦差了 5 个"，而是"这份文档到底靠不靠谱？"**

一致性检查不是整理文件的洁癖行为，而是维护团队对规划的信任。一旦信任破裂，规划就变成了"仅供参考"的废纸。

### 认知 5：任何不可精确测量的目标都是愿望，不是规划

ChatBI 的核心价值是"3 秒"，但工程规划中全链路最坏情况 15-20 秒。Phase 2 目标是"准确率 > 70%"，但没有定义当前基线。

> **marketing claim 和 engineering reality 之间的 gap，是产品规划中最危险的未爆炸弹。不是因为它做不到，而是因为它没有被正确定义——是 P50 还是 P95？缓存命中算不算？**

"从 X 提升到 Y" 和 "达到 Y" 是完全不同的两件事。没有基线的目标只是一个愿望，不是规划。

**ChatBI 的全链路时间预算**：Intent(200ms) → Schema(1s) → SQL(3s) → AST(100ms) → Cache(50ms) → Execute(5s) → Chart(500ms) → SSE 流式输出。最坏情况 ~15s，不是 3s。

**成本量化**：单次查询约 $0.048（Sonnet），1000 次/天 = $48/天 = $1,440/月。优化手段：语义缓存 30-50% 命中、Column Prune 节省 40-60% token、模型路由节省 31-80%。不做成本规划 = 预算失控。

**行业基准的陷阱**：Spider/BIRD/Spider 2.0 标注错误率 52.8%-62.8%。公开基准对生产环境参考价值有限——必须构建内部测试集（每个数据源 20-50 个标准 QA 对），每次代码变更自动运行，测量执行准确率。

### 认知 6：自己永远看不到自己的盲点

> **写文档的人的注意力已经"锁定"在当前的理解框架里了。即使他反复读自己的文档，也只能在已有的理解范围内发现问题。真正有价值的审查来自"不知道你在想什么"的人。**

这解释了为什么"自查"只能发现格式和数字错误，而独立审查才能发现结构性遗漏。

**ChatBI 盲点典型案例**：
- **LLM Provider 故障转移**：一开始只配了单一 LLM，第 2 轮审查才意识到需要 OpenAI/Anthropic/Dashscope 自动切换（一个挂了就切另一个）
- **三管道模式**：一开始只设计了"用户提问 → 系统回答"一个流程，第 3 轮才发现实际有三种管道：Indexing（预计算）、Ask（首次查询）、Follow-up（上下文继承追问），每种管道的工作流完全不同

### 认知 7："不做"定义了产品的边界

> **不做什么是产品规划的"负面空间"——它定义了产品的边界。没有边界的产品注定会范围蔓延，因为"一切都有道理做"。决定"不做"什么，是产品决策中唯一能真正保护团队注意力的行为。**

**ChatBI v1 明确不做的**：
- 不做多数据源 JOIN 查询（跨库关联太复杂，v2 再做）
- 不做实时数据同步（定时扫描即可）
- 不做自定义 SQL 编辑器（面向不会 SQL 的用户）
- 不做移动端适配（B 端产品，桌面优先）
- 不做 AI 自动生成看板（先跑通单次查询）

### 认知 8：规划阶段的"慢"是为了执行阶段的"快"

ChatBI 规划阶段投入约 12 小时，换来的是：执行阶段开发者拿到可直接开工的文档、避免了至少 15+ 个执行阶段才会发现的遗漏、避免了前后端对接时的反复沟通。

> **规划阶段的每个小时，大约能节省执行阶段 3-5 小时的返工。但更关键的是，规划避免的那些"写到一半发现方案错了"的重构，其代价不是按小时算的，是按周算的。**

### 认知 9：核心难题必须有 Plan B

对每个"决定产品生死"的技术难题，不能假设"一定能成"。必须定义：如果这个方案失败了，什么时候 Kill？什么时候 Pivot？Plan B 是什么？

### 认知 10：规划文档的"最小可用信息量"

> **规划文档不是越长越好，也不是越短越好。它的"最小可用信息量"是：一个完全不了解这个项目的开发者，读完之后能直接开始写代码，而不需要向任何人提问。**

如果开发者还需要问"密码怎么存？"、"环境变量有哪些？"、"API 错误返回什么格式？"——说明规划还没到"可执行"的程度。

**"最小可用信息量"的测试**：把文档给一个完全不了解这个项目的开发者，看他多久能开始写第一个 PR。如果还需要问超过 3 个问题，说明文档还不够。

## 第六部分：从 0 到 1 执行阶段的经验总结

> **规划只是开始，执行才是检验真理的地方。以下每一条都是从实际开发和测试中踩出来的教训。**

### 一、环境配置集中化

**教训**：一开始超时、限流、LLM 参数等硬编码在 13 个文件里，改一个值要翻多个文件。

**做法**：所有配置集中到 `config.py`，通过环境变量控制。`.env.example` 同步更新。新增约 30 个配置项。

**检查项**：
- [ ] 所有魔法数字（超时、阈值、默认值）是否都提取到配置类？
- [ ] `.env.example` 是否包含所有必填/选填变量？
- [ ] 默认值是否在无 `.env` 时也能启动？

### 二、测试必须跑真实数据，不能用假数据库

**教训**：seed 数据里写了 `ecommerce`、`demo_db` 等不存在的数据库，导致数据源连接测试全部失败。看起来"功能正常"，但实际全是 CONNECTION_FAILED。

**做法**：数据源必须指向真实可连的数据库。测试前先用 `SHOW DATABASES` 确认可用库，seed 数据用真实存在的库名和账号。

**检查项**：
- [ ] 所有 seed 数据源是否能实际 `SELECT 1` 成功？
- [ ] 元数据配置（metadata_configs）的 schema 是否来自真实扫描或真实结构？
- [ ] 测试用户能否真实登录（密码 hash 正确、邮箱验证状态正确）？

### 三、JWT token 必须包含所有权限判断需要的字段

**教训**：JWT 里没有 `role` 字段，导致 `/audit` 接口的 admin 检查永远失败。即使是 admin 也 403。这个 bug 在单元测试里没被发现（因为测试不验证角色逻辑）。

**做法**：登录创建 token 时，把所有后续鉴权需要的字段都写进去：`user_id`、`email`、`tenant_id`、`role`。刷新 token 时同样。

**检查项**：
- [ ] JWT payload 是否包含所有 downstream 鉴权需要的字段？
- [ ] 刷新 token 是否也包含完整字段？
- [ ] 权限判断是否基于 JWT 字段而不是重新查 DB（性能和一致性）？

### 四、异步 ORM 的 merge vs add

**教训**：SQLAlchemy async session 的 `merge()` 返回 coroutine，需要 `await`。而 `add()` 是同步方法，直接调用即可。seed 脚本用 `merge()` 但没 await，导致数据根本没写入。

**做法**：批量插入用 `session.add()` 然后 `commit()`。如果需要用 merge（upsert），必须 `await session.merge(obj)`。

### 五、测试隔离：单元测试用 SQLite，不影响真实数据库

**做法**：`conftest.py` 在导入 app 之前设置 `os.environ["DATABASE_URL"]` 为 SQLite，确保测试不污染开发数据库。每个测试自动建表/删表。

### 六、API 冒烟测试必须覆盖所有核心端点

**教训**：不能只看 health 和 login。每个模块都要测：
- auth: 注册、登录、刷新、锁定、未验证拒绝
- datasources: 列表、创建、测试连接、删除
- queries: 列表、保存、重跑
- feedback: 列表、提交
- audit: admin 可访问、非 admin 拒绝
- export/csv: 正常导出
- conversations: 列表

### 七、测试套件执行规范

**每次代码变更后的测试流程**：
1. `.venv/bin/python -m pytest tests/ -x -q` — 全量测试，确保 192 passed
2. 启动后端 `uvicorn app.main:app` — 确认启动无报错
3. 逐个测试关键 API（至少 login、datasources list、query POST）
4. 验证 MySQL 数据完整性（表行数与预期一致）
5. 数据源连接测试必须返回 `success: true`

### 八、seed 脚本是可复用的基础设施

**做法**：`seed.py` 必须支持重复运行（truncate + insert），每次都能得到一致的数据。UUID 固定（不用随机生成），方便测试引用。

### 九、前端 500 排查清单

当前端说"所有接口都 500"时：
1. 先 `curl health` 确认后端活着
2. 检查前端 proxy target 是否指向正确端口（通常是 8000）
3. 确认没有多个 uvicorn 进程占着端口（`lsof -ti :8000`）
4. 看后端日志里有没有实际收到请求
5. 检查 CORS 配置是否允许前端域名

## 第八部分：执行阶段通用踩坑模式

> **以下每一条都是从实际开发中提炼的通用模式，适用于任何新项目。项目特定细节作为案例附后。**

### 十、外部 API 兼容性不能假设，必须实测

> **任何声称"兼容 OpenAI API"的服务，都可能在某个参数上不兼容。不要看文档，跑测试。**

**通用规则**：
1. 切换外部 API 提供商后，必须跑完整回归测试，不能只看 1-2 个 case
2. 对 API 返回格式做防御性解析：先尝试标准格式，失败则兜底提取（如正则从 markdown 代码块中提取 JSON）
3. 外部 API 的"可选参数"可能被静默忽略，不报错但行为不符合预期（如 `response_format`）
4. 超时是外部 API 最常见的问题，必须设置合理超时 + 降级策略

**ChatBI 案例**：
- DashScope `enable_thinking: true` 返回 70s+，`false` 后降到 1-3s
- 5 个模型中 3 个返回空内容，`response_format` 被静默忽略
- `lingma-qwen3-coder` 是唯一同时支持普通对话 + JSON 模式的模型

**检查项**：
- [ ] 切换外部 API 后是否跑了完整回归测试？
- [ ] 返回格式解析是否有兜底逻辑？
- [ ] 是否设置了超时和降级策略？
- [ ] "可选参数"是否真的生效？有没有静默忽略？

### 十一、缓存只能有一个真相源

> **同时存在本地缓存和远程缓存时，两者的不一致是必然的，不是偶然的。**

**通用规则**：
1. 缓存系统只能有一个真相源（single source of truth），要么全本地，要么全远程
2. 如果必须双写（如 Redis 不可用时降级到内存），降级逻辑必须单向：远程优先 → 内存兜底，且内存数据必须有过期时间
3. 清缓存操作必须覆盖所有层，否则会出现"清了但没完全清"的诡异行为
4. 测试环境的 conftest.py 必须清理所有缓存层（包括内存 fallback）

**ChatBI 案例**：
- `cache_service.py` 同时维护本地 dict + Redis，FLUSHDB 后本地缓存仍命中旧数据
- `login_lock_service.py` 内存中的锁定状态无法被 Redis FLUSHDB 清除
- 限流计数器归零后仍返回 429，重启后端才恢复

**检查项**：
- [ ] 缓存系统是否有且仅有一个真相源？
- [ ] 清缓存操作是否覆盖了所有层？
- [ ] 降级缓存的过期时间是否合理？
- [ ] 测试 conftest 是否清理了所有缓存层？

### 十二、回调/lambda 的参数类型必须与调用方一致

> **回调函数的参数类型由调用方决定，不是由你写回调时的假设决定。**

**通用规则**：
1. 写回调/lambda 前，先确认调用方传什么参数（match 对象？字符串？dict？）
2. `re.sub(pattern, repl, text)` 的 `repl` 如果是 callable，接收的是 `re.Match` 对象
3. 自定义调用 `repl(value)` 传的是原始值，不是 match 对象
4. 这类 bug 的特征：运行时不报错直到触发特定数据，且报错信息容易误导（`'str' has no attribute 'group'` 看起来像是类型错误，实际是调用约定错误）

**ChatBI 案例**：
- `data_masking.py` 的 `lambda m: m.group()[:3]` 把字符串当 match 对象用
- `_mask_value()` 手动调用 `repl(value)` 传字符串，不是 `re.sub` 的回调

**检查项**：
- [ ] 回调函数的参数类型是否与调用方一致？
- [ ] 是否区分了 `re.sub` 回调和手动调用的参数差异？
- [ ] 回调逻辑是否有单元测试覆盖？

### 十三、遍历时不要修改被遍历的集合

> **这是编程 101 的规则，但在流式解析、事件处理等场景中特别容易违反。**

**通用规则**：
1. 遍历数组/列表时，绝不在循环内 `shift()`/`pop()`/`splice()` 修改同一数组
2. 如果需要消费式遍历，用索引 + while 循环，或先复制数组
3. 流式解析（SSE、WebSocket、NDJSON）是重灾区：缓冲区拼接 + 逐行解析，容易在边界条件下出错
4. 这类 bug 的特征：间歇性丢失数据，只在特定数据量或事件顺序下复现

**ChatBI 案例**：
- SSE 解析 `for (const line of lines)` 内用 `lines.shift()` 导致跳过 chart 事件
- 前端显示有数据但无图表类型

**检查项**：
- [ ] 遍历中是否修改了被遍历的集合？
- [ ] 流式解析是否覆盖了所有事件类型？
- [ ] 边界条件（空行、不完整行、多事件同时到达）是否测试过？

### 十四、新增拦截条件必须同步更新测试数据

> **任何新增的"拒绝条件"（权限检查、状态检查、验证检查）都会让已有测试数据失效。**

**通用规则**：
1. 新增登录/访问拦截条件时，第一步是确认已有测试数据能否通过新条件
2. 注册/创建的默认值必须与拦截检查逻辑一致（注册默认 verified=True，否则所有测试用户都无法登录）
3. 测试 fixture 中显式设置所有拦截相关的字段，不依赖默认值
4. 这类 bug 的特征：加了一个小检查，整个测试套件全红

**ChatBI 案例**：
- 添加 `email_verified=False` 时 403 拦截，所有测试用户被拦截
- 注册默认 `email_verified=False`，但登录要求 `True`

**检查项**：
- [ ] 新增拦截条件后，已有测试数据能否通过？
- [ ] 注册/创建的默认值是否与拦截逻辑一致？
- [ ] 测试 fixture 是否显式设置了拦截相关字段？

### 十五、AI 产品的元数据质量决定输出质量

> **LLM 不编造事实的时候，靠的是你给它的上下文。上下文不完整，输出必然错误。**

**通用规则**：
1. AI 产品的准确率瓶颈往往不在模型，而在输入上下文的质量
2. 元数据（表描述、列描述、枚举值说明）缺失时，LLM 只能猜，猜错就是 SQL 错误
3. 自愈/重试无法修复上下文缺失导致的错误（根因是理解错误，不是语法错误）
4. 新增数据源后，补全元数据描述是必做步骤，不是可选步骤

**ChatBI 案例**：
- metadata_config 中文描述为空，LLM 不知道 `t_orders` 就是"订单"
- 生成的 SQL 使用不存在的表名/列名，自愈也无法修复

**检查项**：
- [ ] 每张表/每个关键字段是否有描述？
- [ ] 枚举列（status、type）是否有值说明？
- [ ] 新增数据源后是否补全了元数据？
- [ ] AI 输出错误时，先检查输入上下文还是先调 prompt？

### 十六、API 契约变更必须全链路同步

> **API 响应格式的变更不是"后端改一下就行"，它是一个全链路事件。**

**通用规则**：
1. API 响应格式变更时，必须同步更新：后端代码 → 前端调用 → 测试断言 → 文档
2. 格式迁移期使用兼容性写法（如 `data.get("data", data)`），不要一步到位切换
3. 分页格式变更（offset → cursor）是高风险操作，影响所有列表接口的消费者
4. 这类 bug 的特征：不是功能错误，而是数据解析错误，且只在特定接口上出现

**ChatBI 案例**：
- `page/page_size` → `cursor/page_size`，旧测试 `resp.json()[0]` 报 TypeError
- 前端 saved query 列表解析失败

**检查项**：
- [ ] API 格式变更后，前端、测试、文档是否全部同步？
- [ ] 是否有硬编码旧格式的代码？
- [ ] 迁移期是否使用了兼容性写法？

### 十七、超时是分布式系统最常见的隐性故障

> **超时不会报错，只会让请求"消失"。没有超时监控，你就不知道系统在沉默中失败。**

**通用规则**：
1. 所有外部调用（LLM API、数据库查询、HTTP 请求）必须设置超时，不能无限等待
2. 超时值必须可配置（环境变量），不同环境可能需要不同阈值
3. 超时必须有可观测性：记录超时次数、超时率、P95/P99 延迟
4. 超时后的降级策略必须明确：重试？返回缓存？返回错误？不能让用户无限等待
5. 多层超时要协调：外层超时 > 内层超时之和（如管线总超时 35s > SQL 执行 30s + 其他步骤）
6. 超时阈值不是一成不变的：模型切换、数据量增长、网络变化都可能让原来的阈值不够

**ChatBI 案例**：
- LLM 推理模式（`enable_thinking: true`）返回 70s+，远超 30s 超时
- SQL 执行 30s 超时在复杂查询下不够，需要自愈重试
- 管线总超时 35s 需要覆盖所有子步骤的超时之和
- 切换模型后超时特征完全不同，必须重新校准

**检查项**：
- [ ] 所有外部调用是否设置了超时？
- [ ] 超时值是否可配置？
- [ ] 超时次数/率是否有监控？
- [ ] 超时后的降级策略是什么？
- [ ] 外层超时是否 > 内层超时之和？
- [ ] 切换外部依赖后是否重新校准超时阈值？

### 十八、功能状态必须显式标记，不能靠"默认行为"隐式满足

> **"部分完成"比"未完成"更危险——你以为它工作了，实际上只在 happy path 上工作。**

**通用规则**：
1. 需求追踪表中，"Partial"和"Missing"是两种完全不同的状态，不能混为一谈
2. Partial = happy path 通过但边界条件未覆盖（如多租户隔离只做了数据源，查询层面未强制过滤）
3. Missing = 完全未实现，不会给人"已经做了"的错觉
4. Partial 的需求必须明确标注"哪些场景已覆盖、哪些未覆盖"，否则会误判为已完成
5. 代码中有字段/接口但未实际使用（如 `is_active` 字段存在但查询时未检查），是最危险的 Partial

**ChatBI 案例**：
- TENANT-01 多租户隔离：数据源已隔离，但查询层面未强制 tenant_id 过滤
- DSO-08 数据源启停：`is_active` 字段存在但禁用的数据源仍可查询
- SEC-01 审计日志：有记录但缺少完整查询审计

**检查项**：
- [ ] Partial 需求是否标注了"已覆盖/未覆盖"的场景？
- [ ] 代码中的字段/接口是否被实际使用？
- [ ] 是否存在"有字段但未检查"的 Partial？

### 十九、FastAPI 依赖注入不能手动调用

> **`Depends()` 是 FastAPI 框架的魔法，手动调用 `require_role("admin")(user)` 不等于 `Depends(require_role("admin"))`。**

**通用规则**：
1. FastAPI 的 `Depends()` 由框架在请求处理时自动解析和注入，手动调用绕过了框架的依赖图
2. 权限检查必须通过 `Depends()` 声明在函数签名中，不能在函数体内手动调用
3. 手动调用的特征：权限检查看起来"写了"但实际不生效，或报错信息不标准

**ChatBI 案例**：
- `datasource.py` 的 toggle 端点手动调用 `await require_role("admin")(user)`，绕过了 FastAPI 依赖注入
- 修复：改为 `admin: dict = Depends(require_role("admin"))` 放在函数签名中

**检查项**：
- [ ] 权限检查是否通过 `Depends()` 声明？
- [ ] 是否有手动调用依赖函数的代码？
- [ ] 依赖注入的参数是否在函数签名中？

### 二十、Refresh token 必须包含与 Access token 相同的鉴权字段

> **刷新 token 后生成的新 access token 必须包含完整的鉴权信息，否则刷新后权限丢失。**

**通用规则**：
1. Refresh token 的 payload 必须包含所有鉴权字段（role、tenant_id 等）
2. 刷新端点创建新 token 时，必须从旧 token payload 中提取并传递所有字段
3. 这类 bug 的特征：登录后正常，刷新后权限检查失败

**ChatBI 案例**：
- `auth.py` 的 refresh 端点 `token_data` 缺少 `role` 字段
- 刷新后的 JWT 没有 role，导致 `require_role` 检查失败

**检查项**：
- [ ] Refresh token payload 是否包含所有鉴权字段？
- [ ] 刷新端点是否传递了完整的 token_data？
- [ ] 是否测试了"刷新后权限仍正常"的场景？

### 二十一、MySQL 的 VARCHAR 必须指定长度

> **Alembic 迁移脚本中 `sa.String()` 在 MySQL 方言下会报错，必须指定长度。**

**通用规则**：
1. MySQL 要求 VARCHAR 列必须有长度限制，`sa.String()` 无长度在 MySQL 下编译失败
2. 迁移脚本必须考虑目标数据库方言，不能只看 SQLite 兼容性
3. 长文本列用 `sa.Text()` 而非 `sa.String()`

**ChatBI 案例**：
- 迁移脚本 `sa.String()` 在 SQLite 下通过，MySQL 下报 `VARCHAR requires a length`
- 修复：`sql_text` 改为 `sa.String(5000)`，`generated_sql` 改为 `sa.Text()`

**检查项**：
- [ ] 迁移脚本是否在目标数据库方言下测试过？
- [ ] String 列是否都指定了长度？
- [ ] 长文本列是否用了 Text 类型？

## 第九部分：一句话总结

> **好产品不是靠想出来的，是靠"竞品分析 → 需求定义 → 架构设计 → 反复审查 → 迭代修复"的纪律性流程磨出来的。跳过任何一步，执行阶段都会付出代价。**

规划阶段的"慢"是为了执行阶段的"快"。

### 二十二、SQLAlchemy Model 和 Alembic Migration 必须保持类型同步

> **Model 用 String，Migration 用 Text，在 SQLite 下都通过，在 MySQL 下行为不同。**

**通用规则**：
1. Model 和 Migration 的列类型必须完全一致，不能一个用 String 一个用 Text
2. 长文本/JSON 列统一用 Text，短文本用 String(N)
3. nullable 也必须对齐——Model 中 `Mapped[str]` 默认 nullable=False，但 Migration 可能写了 nullable=True
4. 定期用脚本对比 Model 列和 Migration 列，发现差异立即修复

**ChatBI 案例**：
- Model 的 `config`/`details`/`messages` 等列用 `String`（无长度限制），Migration 用 `Text`
- `AuditLog.resource_type`/`resource_id` Model 中非空，Migration 中 nullable
- 修复：统一为 Text（长文本列），nullable 对齐 Migration

**检查项**：
- [ ] Model 和 Migration 的列类型是否完全一致？
- [ ] nullable 约束是否对齐？
- [ ] 是否有定期同步检查机制？

### 二十三、SSE 流式解析不能在遍历中修改数组

> **`for (const line of lines)` 内用 `lines.shift()` 会导致跳过事件，这是遍历修改的经典 bug。**

**通用规则**：
1. SSE/流式解析用索引遍历 + 手动递增，不用 for-of/for-in
2. 缓冲区拼接后 split，用 `lines.pop()` 取走未完成行，不要 shift 消费已完成行
3. 事件解析必须覆盖所有已知事件类型，未知类型静默跳过

**ChatBI 案例**：
- 前端 SSE 解析用 `lines.shift()` 消费行，导致 chart 事件被跳过
- 修复：改为索引遍历 `let i = 0; while (i < lines.length)`

### 二十四、多轮对话必须传递历史消息到 SQL 生成

> **"上个月的"这种指代需要上下文才能解析，不传历史就是单轮对话。**

**通用规则**：
1. 多轮对话的"上下文"不仅是前端显示，必须传递到 LLM 调用
2. 历史消息格式要包含 role + content + sql（如果有）
3. 传递最近 N 轮即可，不需要全量历史（控制 token 消耗）
