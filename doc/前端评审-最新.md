## MUST-FIX

### 1. Race condition in token refresh (multiple concurrent 401s)
**File:** `frontend/src/api/index.ts:22-49`
**What:** The response interceptor handles 401 by refreshing the token, but there is no locking mechanism. If three API calls fail with 401 simultaneously, three separate `/auth/refresh` requests fire. Each refresh invalidates the previous refresh token (typical JWT rotation), so only one succeeds and the other two redirect to `/login`, kicking the user out.
**Fix:** Implement a refresh-queue pattern with a `isRefreshing` flag and a pending-requests array. Retry queued requests after the single successful refresh.

### 2. Duplicate message IDs break `v-for` keying
**File:** `frontend/src/stores/chatStore.ts:38,49,64,78`
**What:** All message IDs use `` `msg-${Date.now()}` ``. Two messages created within the same millisecond (user message + instant API error, or two rapid error pushes) will share the same ID. Vue uses `:key="msg.id"` in `ChatView.vue:38`, so duplicate keys cause incorrect DOM diffing and stale rendering.
**Fix:** Use a counter-based ID generator or add a random suffix: `` `msg-${Date.now()}-${crypto.randomUUID?.() ?? Math.random().toString(36).slice(2)}` ``.

### 3. Silent clipboard failure (insecure context / unsupported browser)
**File:** `frontend/src/views/ChatView.vue:159-162`
**What:** `navigator.clipboard.writeText` throws in non-HTTPS contexts (HTTP, `file://`) and on older browsers. No try/catch means an unhandled promise rejection.
**Fix:** Wrap in try/catch, show `ElMessage.error('复制失败')` on failure, and optionally fall back to `document.execCommand('copy')`.

### 4. `remove` silently swallows errors -- UI never shows failure
**File:** `frontend/src/stores/datasourceStore.ts:63-69`
**What:** The `remove` function returns an error string but the caller (`DataSourceListView.vue:102`) checks `if (error)`. The problem: on *success*, `remove` returns `undefined` (implicit), which is falsy -- correct. But the `finally` block is missing, so `loading` stays `true` if the API throws. The delete button appears stuck in loading state.
**Fix:** Add `finally { loading.value = false }` to the `remove` function.

### 5. `ChatView.vue` uses `msg` typed as `any` in `submitFeedback`
**File:** `frontend/src/views/ChatView.vue:164`
**What:** `submitFeedback(msg: any, ...)` bypasses the `Message` interface entirely. The function passes `msg.id` as `query_id`, but `Message.id` is a client-generated string (see issue #2), not a server-side `query_id`. The feedback API likely expects a different identifier.
**Fix:** Define the correct payload shape in the `Message` interface (e.g., `serverQueryId?: string`) and use it. Type `msg` as `Message`.

### 6. No `finally` block in `datasourceStore.remove()` leaves loading stuck
**File:** `frontend/src/stores/datasourceStore.ts:63-69`
**What:** Unlike `list()`, `create()`, and `testConnection()`, the `remove` function has no `finally { loading.value = false }`. A failed delete leaves the store in a perpetual loading state, disabling the add-datasource button (line 61 binds to `datasourceStore.loading`).
**Fix:** Add `finally { loading.value = false }`.

### 7. `authStore.login` / `register` return `string | boolean` -- callers cast with `as string`
**File:** `frontend/src/stores/authStore.ts:42-43, 54-55` + `LoginView.vue:58`, `RegisterView.vue:75`
**What:** On error the store returns a string (the error message); on success it returns `true`. Callers do `if (result === true) ... else ElMessage.error(result as string)`. This works by accident -- there is no return type annotation, TypeScript infers `string | boolean | undefined`. If a future change returns `undefined`, the cast silently produces `undefined` in the error toast.
**Fix:** Define `type AuthResult = true | string` and annotate: `async function login(...): Promise<AuthResult>`.

### 8. Missing route for `DataSourceEditView.vue`
**File:** `frontend/src/views/DataSourceEditView.vue` + `frontend/src/router/index.ts`
**What:** `DataSourceEditView.vue` exists ("功能开发中...") but there is no route pointing to it. If someone adds a route later, the view is a stub. If it's intended for future use, it should not be in the source tree yet (dead code).
**Fix:** Either add a `/datasources/:id/edit` route with a proper edit form, or remove the file.

### 9. Password confirmation validator uses untyped parameters
**File:** `frontend/src/views/RegisterView.vue:46`
**What:** `validateConfirm(_rule: any, value: string, callback: any)` -- both `_rule` and `callback` are `any`. The Element Plus `FormItemRule` and `ValidateCallback` types exist but are not imported or used.
**Fix:** Import `type FormItemRule` from `element-plus` and type the validator properly, or use the async validator pattern: `async (_rule, value) => { if (value !== form.password) throw new Error('...') }`.

### 10. `copySql` uses non-null assertion without validation
**File:** `frontend/src/views/ChatView.vue:44`
**What:** `@click="copySql(msg.sql!)"` -- the `v-if="msg.sql"` guard on line 41 makes this safe at runtime, but if the guard is ever removed or changed, the non-null assertion masks the bug. More importantly, `msg.sql` can be an empty string `""` which passes `v-if` (falsy check) but the guard is actually on `msg.sql` truthiness, so this is OK. Still, prefer `v-if="msg.sql"` + no `!` assertion.
**Fix:** Remove `!` and rely on the `v-if` guard: `@click="copySql(msg.sql)"`.

## SHOULD-FIX

### 11. `ChartRenderer` deep watch on `props.rows` re-renders on every data change
**File:** `frontend/src/components/ChartRenderer.vue:146-148`
**What:** `watch(() => [props.chartType, props.rows, props.columns], renderChart, { deep: true })` performs a deep equality check on the entire `rows` array every time any reactive dependency changes. For large result sets (hundreds of rows), this is expensive.
**Fix:** Watch a computed reference like `() => props.rows.length` or use a shallow comparison. ECharts `setOption(option, true)` already handles diffing internally.

### 12. Window resize handler fires without debounce
**File:** `frontend/src/components/ChartRenderer.vue:142-143, 152`
**What:** `handleResize` calls `chart.value?.resize()` on every resize event. Modern browsers fire 60+ resize events per second during a window drag. ECharts `resize()` is relatively cheap but unnecessary at this frequency.
**Fix:** Wrap in `lodash/debounce` or a custom debounce: `const handleResize = debounce(() => chart.value?.resize(), 150)`.

### 13. `ChartRenderer` internal `currentType` drifts from prop
**File:** `frontend/src/components/ChartRenderer.vue:42-46`
**What:** `currentType` is a separate `ref` initialized from `props.chartType`, with a watcher to sync. If the parent updates `chartType` while the user has changed the dropdown, the watcher overwrites the user's choice. The emit on line 133 fires, but the parent may not update, causing a mismatch between UI and prop.
**Fix:** Either make `currentType` fully controlled by the parent (remove the ref, use `props.chartType` directly) or document this as a two-way prop and use `v-model:chartType`.

### 14. `ChartRenderer` returns empty option for unsupported chart types -- silent blank
**File:** `frontend/src/components/ChartRenderer.vue:116`
**What:** If `chartType` is not one of `line/bar/pie/scatter/metric/table`, `getOption()` returns `{}`. The wrapper checks `Object.keys(option).length > 0` and renders nothing. Users see a blank area with no feedback.
**Fix:** Return a fallback option with a "不支持的图表类型" message, or render an `el-empty` state.

### 15. No error boundary in ChartRenderer -- ECharts init failure crashes the component
**File:** `frontend/src/components/ChartRenderer.vue:119-130`
**What:** `echarts.init()` and `setOption()` can throw (e.g., invalid DOM, malformed data). No try/catch means an unhandled exception tears down the component tree.
**Fix:** Wrap `renderChart()` in try/catch, set a local `error` ref, and display an error message.

### 16. `authStore.initFromStorage` called redundantly on every route change AND on mount
**File:** `frontend/src/router/index.ts:44-45` + `ChatView.vue:186`
**What:** `router.beforeEach` calls `authStore.initFromStorage()` on every navigation. `ChatView.onMounted` calls it again. `initFromStorage` has a guard `if (!user.value)`, but this is still redundant and couples the router to store implementation details.
**Fix:** Call `initFromStorage()` once in `main.ts` after creating the Pinia app, before `app.mount('#app')`. Remove from router guard and component mounts.

### 17. Switching datasource silently clears all messages
**File:** `frontend/src/views/ChatView.vue:181-183`
**What:** `onDatasourceChange` calls `chatStore.clearMessages()` with no confirmation. A user accidentally clicking the dropdown loses their entire conversation history.
**Fix:** Add an `ElMessageBox.confirm` before clearing, or at minimum show an `ElMessage.warning` toast.

### 18. Global icon registration loads 200+ unused icons
**File:** `frontend/src/main.ts:14-16`
**What:** `Object.entries(ElementPlusIconsVue)` registers every icon globally. `@element-plus/icons-vue` exports 200+ icons. Only 6 are used (`Message`, `Lock`, `ChatDotRound`, `Loading`, `CircleCheckFilled`, `CircleCloseFilled`, `Close`, `Folder`, `Document`). This increases bundle size and pollutes the global component namespace.
**Fix:** Register only needed icons individually, or use the auto-import approach with `unplugin-icons`.

### 19. `DataDictionary` uses `any[]` for tables and column definitions
**File:** `frontend/src/components/DataDictionary.vue:47, 54`
**What:** `tables` is typed `any[]` and column mapping uses `c: any`. The schema API response structure is unknown to TypeScript, so typos in property access (`c.data_type`, `c.comment`, `c.primary`) are not caught.
**Fix:** Define `interface SchemaTable { name: string; description?: string; columns: SchemaColumn[] }` and `interface SchemaColumn { name: string; type?: string; data_type?: string; comment?: string; primary?: boolean }`.

### 20. No client-side validation on datasource create form
**File:** `frontend/src/views/DataSourceListView.vue:34-57, 110-114`
**What:** The form has `required` attributes on labels but no Element Plus form rules. Validation is a manual `if (!form.name || ...)` check that does not highlight which field is missing. The port number can still be invalid (e.g., 0).
**Fix:** Add `el-form` `:rules` with required validators for name, host, database_name, username, password. Add port range validation (1-65535).

### 21. No `catch` on `auth/register` error path in RegisterView
**File:** `frontend/src/views/RegisterView.vue:70-76`
**What:** `authStore.register` returns `true | string`. But if the API throws a non-HTTP error (network failure, timeout), the catch in the store returns the error string. However, if the store itself throws (e.g., a bug in `atob`), it propagates uncaught.
**Fix:** The store's catch handles this, but the store function should have an explicit return type to make the contract clear (see #7).

### 22. Metric card shows column name as label, not a user-friendly name
**File:** `frontend/src/components/ChartRenderer.vue:17`
**What:** `<div class="metric-label">{{ columns[0] }}</div>` -- if the column is `sum_total_amount_usd`, it displays exactly that. No formatting or humanization.
**Fix:** Add a `label` prop to ChartRenderer, or format the column name (e.g., split underscores, capitalize).

## NICE-TO-HAVE

### 23. No ESLint, Prettier, or editorconfig
**What:** `tsconfig.json` has `noUnusedLocals: false` and `noUnusedParameters: false`, which suppresses useful warnings. No linting or formatting tooling exists.
**Impact:** Inconsistent code style, dead code goes unnoticed.
**Fix:** Add `eslint` with `@vue/eslint-config-typescript`, `prettier`, and `.editorconfig`. Enable `noUnusedLocals` and `noUnusedParameters`.

### 24. No test files at all
**What:** Zero test files. No Jest/Vitest config. No `__tests__` directories.
**Fix:** Add Vitest + Vue Test Utils. At minimum, test: auth store login/logout flow, chat store message appending, router guards.

### 25. `vite.config.ts` missing `base` for non-root deployments
**File:** `frontend/vite.config.ts`
**What:** If the app is deployed under a subpath (e.g., `/chatbi/`), all asset URLs break because `base` defaults to `/`.
**Fix:** Add `base: process.env.VITE_BASE_PATH || '/'`.

### 26. No `env.d.ts` content shown (referenced in tsconfig but not in file list)
**File:** `frontend/tsconfig.json` includes `env.d.ts` but it was not in the file listing.
**What:** Without `env.d.ts` declaring `*.vue` modules, TypeScript cannot type-check `.vue` imports properly. It may exist but was missed.
**Fix:** Ensure `env.d.ts` contains: `declare module '*.vue' { import type { DefineComponent } from 'vue'; const component: DefineComponent<{}, {}, any>; export default component; }`

### 27. Global styles in App.vue are unscoped and minimal
**File:** `frontend/src/App.vue:5-15`
**What:** `.page-container` sets `max-width: 1200px` which is reasonable for desktop but not responsive. No media queries exist anywhere in the codebase. Mobile users get a cramped experience.
**Fix:** Add responsive breakpoints or use CSS `clamp()`/`max()` for fluid sizing.

### 28. No loading state for datasource list on initial ChatView mount
**File:** `frontend/src/views/ChatView.vue:185-191`
**What:** `onMounted` calls `datasourceStore.list()` but the datasource selector (`el-select`) shows no loading indicator. Users see an empty dropdown and may think there are no datasources.
**Fix:** Bind `:loading="datasourceStore.loading"` to the `el-select`, or show a spinner while loading.

### 29. FirstUseGuide dynamic import for analytics is clever but fragile
**File:** `frontend/src/components/FirstUseGuide.vue:78-83`
**What:** `import('@/api').then(({ default: api }) => ...)` is a dynamic import to avoid circular dependencies. It works but is unconventional. If `@/api` is already loaded, this is just a reference to the existing module.
**Fix:** The pattern is fine for avoiding circular deps, but a comment explaining why would help. Consider restructuring to avoid the circular import entirely.

### 30. `message.user` CSS has white text on colored background -- potential contrast issue
**File:** `frontend/src/views/ChatView.vue:281-284`
**What:** User messages use `#667eea` background with white text. The contrast ratio is approximately 4.6:1, which passes WCAG AA for normal text but is close to the threshold. For users with visual impairments, this may be hard to read.
**Fix:** Consider a slightly darker shade (e.g., `#5568d8`) for better contrast.
