# ChatBI Backend — Architecture Review (Fresh Audit)

**Audit Date:** 2026-05-02
**Scope:** All `.py` files under `backend/app/` and `backend/tests/`

---

## 1. MUST-FIX: Blocking bcrypt in async event loop

**Severity:** MUST-FIX
**File:** `app/core/security.py:17-24`, `app/api/auth.py:95`

The `bcrypt.hashpw()` and `bcrypt.checkpw()` calls in `verify_password()` and `hash_password()` are synchronous CPU-bound operations. They are invoked from async route handlers (`/api/v1/auth/login`, `/api/v1/auth/register`) which blocks the entire event loop. With `bcrypt_rounds=12` each call takes ~250ms — during that time no other request can be processed.

**Impact:** Under even modest concurrent load (5+ simultaneous logins), the event loop stalls completely. The server becomes unresponsive.

**Fix:** Use `anyio.to_thread.run_sync()` to offload bcrypt to a worker thread, or switch to `passlib` with its async support:
```python
import anyio
async def verify_password(password: str, hashed: str) -> bool:
    return await anyio.to_thread.run_sync(
        bcrypt.checkpw, password.encode("utf-8"), hashed.encode("utf-8")
    )
```

## 2. MUST-FIX: SQL injection via user-controlled string concatenation

**Severity:** MUST-FIX
**File:** `app/api/query.py:60`, `app/services/datasource_service.py:86-90`

In `datasource_service.py:86-90`, the test_connection method builds a database URL by interpolating decrypted username and password directly into the connection string:
```python
url = f"mysql+aiomysql://{username}:{password}@{ds.host}:{ds.port}/{ds.database_name}"
```
While these values come from encrypted storage, if an attacker ever writes to the `data_sources` table (e.g., via a future admin endpoint), malicious characters in host/database_name could inject connection parameters.

More critically, in `app/api/query.py` the `data.question` field flows directly into LLM prompts with no input sanitization. While the LLM is instructed to only generate SELECT statements, prompt injection via the natural language input is a real attack vector.

**Impact:** Potential unauthorized database access via crafted connection strings; prompt injection could generate arbitrary SQL.

**Fix:** (1) Use SQLAlchemy's URL builder: `URL.create("mysql+aiomysql", username=..., password=..., host=..., port=..., database=...)`. (2) Add a secondary SQLGlot validation layer after LLM generation that parses the generated SQL into an AST and rejects any non-SELECT nodes before execution. The current `validate_sql` in `execution.py:29-33` uses string matching (`if kw in upper_sql`) which is bypassable — e.g., `SELECT * FROM users WHERE name = 'DROP TABLE'` would be rejected by the keyword check, but `SELECT /*! DROP */ ...` could bypass it.

## 3. MUST-FIX: Race condition in login lock (in-memory, process-local)

**Severity:** MUST-FIX
**File:** `app/services/login_lock_service.py:6`, `app/api/auth.py:81`

The login lock uses a plain Python dictionary `_login_attempts: dict[str, dict] = {}` as module-level state. This means:
- **Multi-process deployment:** If running with `uvicorn --workers N`, each worker has its own copy. An attacker can bypass the lock by hitting different workers.
- **Server restart:** All lock state is lost. Brute-force attacks resume immediately after restart.
- **`check_lock` vs `record_failure` gap:** There is no atomicity between checking the lock and recording a failure. Two concurrent login requests for the same user could both read `count=4`, both increment to 5, and neither triggers the lock.

**Impact:** Login lock is completely ineffective in production with multiple workers. Concurrent login attempts can race past the lock threshold.

**Fix:** Move login lock state to Redis (which is already a stated future dependency per `main.py:52`) or to the database. Use atomic `INCR` + `EXPIRE` operations with a database row in `users.failed_login_attempts` as the source of truth.

## 4. MUST-FIX: Connection pool leak — pools never disposed on credential change

**Severity:** MUST-FIX
**File:** `app/services/connection_pool.py:15-48`

The `ConnectionPoolManager` caches `AsyncEngine` instances by datasource ID in `_pools: dict[str, AsyncEngine]`. When a datasource's credentials are updated via `PUT /datasources/{ds_id}`, the old pool remains active with stale credentials. New queries will use the cached engine with old (possibly revoked) credentials until the server restarts.

Similarly, the `test_connection` method in `datasource_service.py:91` creates a brand-new `create_async_engine()` every time, but the pool in `connection_pool.py` is never updated to match.

**Impact:** Stale connections with revoked credentials persist indefinitely. Memory grows linearly with the number of test_connection calls that fail to use the cached pool.

**Fix:** Add a `refresh_pool(ds_id, ds)` method that disposes the old engine and creates a new one. Call it from `DataSourceService.update()`. Also, consolidate all engine creation through the pool manager — don't create ad-hoc engines in `test_connection`.

## 5. MUST-FIX: Export endpoint returns dict on error but Response on success

**Severity:** MUST-FIX
**File:** `app/api/export.py:20-57`

The `export_csv` endpoint returns `{"error": "..."}` (a Python dict) when no data is available, but returns a `Response` object on success. FastAPI will try to serialize the dict as JSON for one branch and raw bytes for the other. This is inconsistent and will cause the dict error case to be JSON-serialized while the success case is raw CSV — the client cannot handle both.

Additionally, the error response uses a plain string dict instead of the project's `_error()` helper pattern used everywhere else.

**Fix:** Use `JSONResponse` or `HTTPException` for the error case:
```python
if not columns or not rows:
    raise HTTPException(status_code=404, detail=_error("NO_DATA", "无数据可导出"))
```

## 6. MUST-FIX: Missing rate limiting in production

**Severity:** MUST-FIX
**File:** `app/main.py:52-54`

The rate limiter middleware is commented out with a TODO: "enable when Redis is available." The in-memory rate limiter in `app/core/rate_limiter.py` is fully implemented and functional but never mounted. This means:
- No protection against brute-force login attacks beyond the broken in-memory lock
- No protection against query spam (each query costs LLM API calls)
- No protection against data exfiltration via repeated exports

**Impact:** The API is completely open to abuse in production.

**Fix:** Enable the existing rate limiter middleware immediately. It works without Redis — the TODO comment is misleading. The in-memory limiter is better than nothing, and Redis can be added later as an upgrade path.

## 7. SHOULD-FIX: Double commit in auth and saved_query routes

**Severity:** SHOULD-FIX
**File:** `app/api/auth.py:104,118`, `app/api/saved_query.py:87,93`

In `auth.py:104`, `await db.commit()` is called after resetting login attempts, then again at line 118 after audit/analytics events. If the second commit fails (e.g., analytics insert fails), the first commit's changes (login attempt reset) are already persisted — creating an inconsistent state where the login succeeded but audit/analytics are missing.

Same pattern in `saved_query.py:87` (save query commit) then `:93` (analytics commit).

**Fix:** Perform all writes within a single transaction and commit once at the end:
```python
# ... all db operations ...
await db.commit()  # single commit
```

## 8. SHOULD-FIX: Stream query endpoint bypasses transaction management

**Severity:** SHOULD-FIX
**File:** `app/api/query.py:134-220`

The `/query/stream` endpoint opens a database session via `Depends(get_db)` but never commits or rolls back. The `event_stream()` generator runs after the route handler returns the `StreamingResponse`, and by that time FastAPI may have already cleaned up the DB session dependency. Any DB operations inside the generator (if added later) would operate on a closed session.

Additionally, the stream endpoint has no audit logging or analytics tracking — the non-stream endpoint logs both, creating an observability gap.

**Fix:** Either (a) wrap the generator in a context manager that holds the session open, or (b) explicitly manage the session lifecycle within `event_stream()`. Add audit/analytics tracking to match the non-stream endpoint.

## 9. SHOULD-FIX: datasource_id type mismatch between UUID and string

**Severity:** SHOULD-FIX
**File:** `app/api/saved_query.py:84`, `app/db/models.py:88`

In `saved_query.py:84`, `datasource_id` is stored as a plain string from the request body (`data.get("datasource_id")`), but the model defines it as `Mapped[uuid.UUID]`. SQLAlchemy's custom `GUID` type handles the conversion, but the inconsistency means:
- If a non-UUID string is passed, it will be stored as-is and fail on later joins
- The `get_by_id` in `datasource_service.py:38` does `uuid.UUID(ds_id)` which will raise `ValueError` for malformed IDs

**Fix:** Use a Pydantic schema for the save_query request body (currently accepts raw `dict`), with `datasource_id: UUID`. This ensures validation at the API boundary.

## 10. SHOULD-FIX: LangGraph graph rebuilt on every request

**Severity:** SHOULD-FIX
**File:** `app/api/query.py:68`, `app/ai/graph.py:37-116`

`build_graph()` constructs a new `StateGraph` and compiles it on every query request. Graph compilation involves importing modules, creating node functions, and setting up the state machine — this is expensive and unnecessary.

**Fix:** Build and compile the graph once at startup (in `lifespan` or at module import time) and reuse the compiled instance:
```python
# At module level in app/ai/graph.py
COMPILED_GRAPH = build_graph()  # called once
```

## 11. SHOULD-FIX: SQL validation uses string matching, not AST

**Severity:** SHOULD-FIX
**File:** `app/ai/nodes/execution.py:29-33`

The dangerous keyword check uses substring matching:
```python
dangerous_keywords = ["DROP", "DELETE", ...]
for kw in dangerous_keywords:
    if kw in upper_sql:
        return False, f"禁止使用 {kw} 语句"
```
This has two problems:
1. **False positives:** `SELECT * FROM users WHERE name = 'DELETE ME'` would be rejected.
2. **Bypassable:** SQL comments or alternative syntax can bypass string checks. The SQLGlot parse on line 21 already produces an AST — use it: check `isinstance(parsed, sqlglot.exp.Select)` is correct, but also walk the AST tree for any `Drop`, `Delete`, `Insert` nodes instead of string scanning.

**Fix:** After the `isinstance(parsed, sqlglot.exp.Select)` check, walk the AST for dangerous node types:
```python
for node in parsed.walk():
    if isinstance(node, (sqlglot.exp.Drop, sqlglot.exp.Delete, ...)):
        return False, "禁止使用危险语句"
```

## 12. SHOULD-FIX: No pagination metadata returned

**Severity:** SHOULD-FIX
**File:** `app/api/saved_query.py:21-50`, `app/api/feedback.py:44-69`, `app/api/audit.py:13-48`

All list endpoints accept `page` and `page_size` parameters but return only the raw list. Clients have no way to know the total count or whether there are more pages. They must either assume infinite pages or implement their own pagination detection.

**Fix:** Return a standard paginated response:
```python
{
    "items": [...],
    "total": 142,
    "page": 1,
    "page_size": 20,
    "has_next": true
}
```

## 13. SHOULD-FIX: LLM instances created per-request

**Severity:** SHOULD-FIX
**File:** `app/ai/nodes/intent.py:24-30`, `app/ai/nodes/generation.py:11-18`

`ChatOpenAI` is instantiated fresh on every intent classification and SQL generation call. While `langchain` clients are lightweight, creating them per-request means connection pooling to the LLM API is not reused, and API key rotation requires server restart.

**Fix:** Create a single `ChatOpenAI` instance at module level and reuse it, or use a factory with caching.

## 14. SHOULD-FIX: Self-healing has unbounded recursion in edge cases

**Severity:** SHOULD-FIX
**File:** `app/ai/nodes/self_heal.py:48-103`

The `self_heal_sql` function is recursive with `MAX_RETRY = 2`, but the recursion happens in multiple paths: empty LLM response (line 80), invalid SQL (line 87), execution failure (line 99), and LLM exception (line 103). If the LLM consistently returns empty responses, the function recurses 3 times per "retry cycle" (empty -> invalid -> execution failure -> retry), potentially exceeding `MAX_RETRY` semantics.

More critically, every recursive call creates a new LLM invocation, which costs API credits and adds latency.

**Fix:** Convert to an iterative loop with explicit retry counting:
```python
for attempt in range(MAX_RETRY):
    # generate, validate, execute
    # break on success, continue on failure
```

## 15. SHOULD-FIX: Feedback endpoint accepts unvalidated dict

**Severity:** SHOULD-FIX
**File:** `app/api/feedback.py:18-41`

The `create_feedback` endpoint accepts a raw `dict` parameter with no Pydantic validation. It extracts `rating`, `query_id`, and `comment` with `.get()` and defaults. A malformed request can create feedback entries with empty `query_id` or invalid ratings that bypass the `"up"/"down"` check (though the check exists, it's after the fact).

**Fix:** Define a `FeedbackCreate` Pydantic model with proper field validation.

## 16. NICE-TO-HAVE: Create tables on every startup

**Severity:** NICE-TO-HAVE
**File:** `app/main.py:26-27`

```python
async with engine.begin() as conn:
    await conn.run_sync(Base.metadata.create_all)
```

This creates/alters tables on every application startup. Alembic is a dependency but is not used. In production with multiple pod replicas, concurrent `create_all` calls can cause race conditions on schema creation.

**Fix:** Use Alembic for migrations. Set `ALEMBIC_MIGRATE=true` env var to control migration behavior. Only run `create_all` in development/test environments.

## 18. NICE-TO-HAVE: No request ID / correlation ID in logging

**Severity:** NICE-TO-HAVE
**File:** `app/core/logging.py:7-20`

The `JSONFormatter` supports `request_id`, `tenant_id`, `user_id`, and `duration_ms` as optional fields, but there is no middleware that populates these fields. Logs from a single request cannot be correlated.

**Fix:** Add a middleware that generates a `request_id` (UUID) per request, extracts `tenant_id`/`user_id` from the auth context, and attaches them to the log record using `logging.LoggerAdapter` or `contextvars`.

## Summary

| Severity | Count | Key Themes |
|----------|-------|------------|
| MUST-FIX | 6 | Blocking I/O, SQL injection risk, broken login lock, connection pool leak, inconsistent API responses, missing rate limiting |
| SHOULD-FIX | 9 | Double commits, transaction leaks, type mismatches, unvalidated inputs, inefficient LLM usage, missing pagination |
| NICE-TO-HAVE | 5 | Schema management, info leakage, observability gaps, test duplication, error format consistency |

The codebase has a solid foundation: clear layer separation (`api/`, `services/`, `ai/`, `db/`, `schemas/`), proper async patterns with SQLAlchemy, Pydantic validation on most inputs, and a well-structured LangGraph query pipeline. The critical issues are mostly around **runtime correctness under production conditions** — blocking crypto calls, in-memory state in a multi-process world, and connection lifecycle management — rather than fundamental architectural flaws.
