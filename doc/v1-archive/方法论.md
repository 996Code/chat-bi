# 新产品规划方法论 — 从 0 到可执行的完整流程

> 适用于任何软件产品的规划阶段。基于 ChatBI 项目的完整规划经验提炼。
>
> **核心信念**：规划不是"预测未来会发生什么"，而是"提前想清楚所有可能失败的方式，然后逐一排除"。

---

## 第一章：为什么必须做规划

### 不规划的代价

大多数项目跳过系统规划直接开干，结果是：
- 写到第 3 周发现核心方案选错了，要重构（代价：按周算）
- 需求边界模糊，"这个功能我以为你做了"
- 前后端对接时发现字段名对不上
- 上线前才发现密码没加密、日志没记、测试没写
- 团队对"产品到底是什么"理解不一致

**规划的本质不是写文档，而是让团队对"做什么、怎么做、为什么这么做"达成一致，避免执行阶段的返工和冲突。**

### ROI

规划阶段每投入 1 小时，预计能节省执行阶段 3-5 小时的返工时间。更关键的是，规划避免的那些"写到一半发现方案错了"的重构，代价不是按小时算，是按周算。

## 第二章：规划流程的 10 个阶段

### 阶段 1：一句话定义产品

用一句话描述产品的核心价值：

> **[目标用户] 通过 [产品做什么]，实现 [用户得到的结果]，在 [关键指标] 内。**

**检查标准**：用户视角（不是技术视角）、有可衡量指标、不懂技术的人能听懂、包含目标用户。

**常见错误**：

| 错误 | 例子 | 问题 |
|------|------|------|
| 技术视角 | "基于 LLM 的 Text-to-SQL 平台" | 用户不关心你用什么技术 |
| 没有指标 | "让用户轻松查询数据" | "轻松"不可衡量 |
| 目标模糊 | "面向企业的数据分析工具" | 太宽泛 |
| 太长 | 一段话都说不完 | 说明还没想清楚 |

### 阶段 2：竞品分析（深度，不是浅度）

**选 3-4 个竞品**：至少 1 个直接 + 1 个间接 + 1 个反面教材。

**每个竞品深挖 4 个维度**：
- **架构**：看源码（如果是开源的）
- **官方博客/技术博客**：踩过什么坑
- **Issues/用户反馈**：真实痛点
- **差异化**：强/弱在哪？我们能更好吗？

**关键产出**：每个竞品发现必须对应一个我们自己的设计决策。

| 竞品发现 | 我们的决策 | 理由 |
|---------|-----------|------|
| 竞品 A 准确率提升靠语义层 | 我们也做语义层 | 验证过的路径 |
| 竞品 B 用 Agent 框架失控 | 我们用确定性工作流 | 避免失控 |

**教训**：竞品分析是给自己避雷用的，不是交差。每个发现必须对应一个"我们怎么做"的决策。

### 阶段 3：需求定义（分类 + 编号 + 优先级）

**按功能域分类，每个需求唯一 ID**：

| 分类 | 含义 | 示例 |
|------|------|------|
| AUTH | 认证与授权 | AUTH-01: 邮箱密码注册 |
| CORE | 核心业务逻辑 | CORE-01: 自然语言转 SQL |
| DS/DATA | 数据源/处理 | DS-01: 连接 MySQL |
| API | 接口设计 | API-01: RESTful API |
| UI/UX | 用户体验 | UX-01: 首次使用引导 |
| SEC | 安全 | SEC-01: 审计日志 |
| PERF | 性能 | PERF-01: 缓存策略 |
| OPS | 运维 | OPS-01: CI/CD 流水线 |

**每个需求的格式**：
```
- [ ] **分类-编号**: 简短描述（括号内补充说明）
  优先级: P0 | P1 | P2 | P3
  Phase: Phase X
  验收标准: 怎么算完成
```

**Out of Scope 必须明确列出**（功能 + 不做的原因 + 什么时候做）。

**关键教训**：
- 需求不是一次性写完的，至少做 3 轮补遗
- **"显性需求"和"隐性基础设施需求"的比例约 1:1**
- Out of Scope 和 In Scope 一样重要

### 阶段 4：需求到 Phase 的追溯映射

每个需求有且仅有一个 Phase 归属。**一致性检查（每次更新后必做）**：

```
1. 需求 checkbox 数量 = 追溯表行数
2. 追溯表中每个需求 ID 在 checkbox 列表中存在
3. 每个 checkbox 在追溯表中有对应行
4. 各 Phase 需求数量之和 = 总需求数量
5. 所有文件中的覆盖率声明 = 实际数量
```

### 阶段 5：架构设计（先解决最难的）

**步骤**：
1. 列出决定产品生死的 3 个技术难题（问自己："如果这个做不成，产品还有价值吗？"）
2. 对每个难题：为什么难 → 业界最佳实践 → 我们的方案 → Plan B
3. 画核心流程图（用户操作 → 系统响应，标注耗时、失败点、回退机制）
4. 分层架构设计（前端 → API → 业务 → 数据 → 存储）

**教训**：架构设计不要从"选框架"开始，要从"最难的难题"开始。

### 阶段 6：技术栈选型

每个技术组件必须有选型表：**候选 / 选择 / 理由 / 淘汰了什么 / 为什么淘汰**。

**选型原则**：团队熟悉度 > 技术先进性；v1 选轻量，v2 再换生产级；不要为了"新技术"引入团队不熟悉的东西。

### 阶段 7：基础设施清单（最容易遗漏的部分）

**认证与安全**：
- [ ] 密码存储策略（hash 算法 + cost factor）
- [ ] 邮箱验证流程
- [ ] 密码重置流程
- [ ] 登录失败保护（锁定/限流）
- [ ] JWT / Session 策略（过期时间、刷新机制）
- [ ] CORS 跨域配置
- [ ] SQL 注入 / XSS 防护
- [ ] 审计日志
- [ ] 敏感数据加密存储

**基础设施**：
- [ ] 环境变量清单（.env.example）
- [ ] 日志策略（格式、级别、correlation ID、PII 脱敏）
- [ ] 数据库表设计（DDL + 索引 + 外键）
- [ ] 数据库迁移工具（Alembic / Flyway / Prisma）
- [ ] Docker / Docker Compose 配置
- [ ] .gitignore
- [ ] CI/CD 流水线
- [ ] 备份与恢复策略

**开发体验**：
- [ ] 本地开发环境一键启动
- [ ] 测试策略（单元 + 集成 + E2E + 覆盖率门控）
- [ ] 代码风格工具（lint、format、pre-commit）
- [ ] API 文档自动生成
- [ ] 错误处理策略

**特定领域（按产品类型补充）**：
- [ ] **BI/数据产品**: 时区处理（UTC 存储 + 用户时区转换）、JOIN 陷阱（Fan Trap / Chasm Trap）、SQL 错误分类与自纠错
- [ ] **AI/LLM 产品**: LLM Provider 故障转移（至少 2 个 provider 自动切换）、单次查询成本预算（token × 单价）、内部测试集（每个场景 20-50 个标准 QA 对）、语义缓存策略（相似度阈值 + 多层缓存）、多管道架构识别（Indexing / Ask / Follow-up 是否都设计了）
- [ ] **国际化产品**: i18n 方案、日期/数字格式化
- [ ] **文件产品**: 上传大小限制、文件类型校验
- [ ] **实时产品**: WebSocket / SSE 协议设计
- [ ] **支付产品**: 幂等性设计、退款流程

**教训**：这个清单应该在需求定义阶段就逐项检查，不要等写到代码才想起来。

### 阶段 8：API 设计（前后端契约）

所有 API 统一格式：**方法 + 路径 + 说明 + 请求体 + 响应体 + 权限 + Phase**。

**标准响应格式**：
```json
// 成功    { "data": { ... }, "code": 0, "message": "success" }
// 错误    { "code": "ERROR_CODE", "message": "用户可读提示", "details": { ... } }
// 分页    { "data": [...], "pagination": { "cursor": "...", "has_more": true, "total": 100 } }
```

**教训**：API 设计要在前端开发前完成，否则前后端反复返工。

### 阶段 9：多轮独立审查

1. **第一轮：自查**（逻辑、数字、引用）
2. **第二轮：独立审查者**（不知道规划内容的人/agent）
3. **第三轮：换一个审查者**（不要用同一个）
4. **第四轮：一致性自动化检查**

**教训**：每次审查都一定会发现遗漏，没有一轮是"白跑"的。**自己写的东西永远看不到自己的盲点。**

### 阶段 10：执行规划（并行化）

- 按依赖关系分 Wave（零依赖 → 依赖 A → 依赖 B）
- 每个 Wave 内最大并行度
- 每个任务有明确的文件归属（防冲突）
- 每个 Wave 有冒烟测试
- 降级策略（卡住了怎么办）
- Kill/Pivot 决策点（Phase X 不达标怎么办）

**AI/LLM 产品额外步骤**：
- **构建内部测试集**：每个场景/数据源 20-50 个标准 QA 对，每次代码变更自动运行
- **验证行业基准适用性**：Spider/BIRD 等公开基准在生产环境参考价值有限，不要盲目采信
- **成本模型验证**：预估单次操作 token 消耗和美元成本，与实际运行对比
- **多管道模式识别**：确认"看起来像一个流程"的东西是否实际是多个不同的操作模式（如首次查询 vs 追问 vs 预计算）

## 第三章：12 个常见陷阱

| # | 陷阱 | 表现 | 对策 |
|---|------|------|------|
| 1 | 技术视角定义产品 | "基于 LLM 的平台" | 用用户视角 |
| 2 | 需求只做一次 | 写了 40 个就觉得够了 | 至少 3 轮补遗 |
| 3 | 竞品分析只看表面 | 只看功能对比表 | 看源码/Issues/博客 |
| 4 | 不做 Out of Scope | 什么都想做 | 明确列出不做的 |
| 5 | 技术选型只说"选了什么" | "后端用 FastAPI" | 必须有淘汰对比 |
| 6 | 忽略"基础设施" | 密码/日志/环境变量全没想 | 用检查清单逐项确认 |
| 7 | 一致性不检查 | 文档间数字不一致 | 每次更新后检查 |
| 8 | 规划文档不被攻击 | 写完就放着 | 找独立审查者 |
| 9 | 核心难题没有 Plan B | 假设一定能成 | 定义 Kill/Pivot 条件 |
| 10 | 没有基线的目标 | "准确率 > 70%"（现在多少？） | 定义基线、测量方法 |
| 11 | 过度设计 | v1 就上 K8s | v1 最小可用链路 |
| 12 | 规划完不验证 | 写了 3000 行没跑过 | 做最小 PoC 验证 |
| 13 | 盲目采信行业基准 | "Spider 准确率 62% 我们也行" | 基准标注错误率 50%+，构建内部测试集 |

## 第四章：规划文档最小集合

| 文档 | 作用 | 建议长度 |
|------|------|---------|
| **PROJECT.md** | 产品概述、核心决策、约束条件 | 50-100 行 |
| **REQUIREMENTS.md** | 需求列表 + 追溯表 | 150-300 行 |
| **ROADMAP.md** | Phase 分解 + 任务 + 依赖 | 100-200 行 |
| **PLANNING.md** | 完整技术规划 | 500-3000 行 |
| **STATE.md** | 项目状态追踪 | 30-50 行 |

## 第六章：执行阶段的 9 条实战经验

> 以下经验来自 ChatBI 项目从规划完成到实际编码、测试、部署的全过程。

### 1. 环境配置集中化

**问题**：超时、限流、LLM 参数等硬编码在十几个文件里，改一个值要翻多个文件。

**做法**：所有配置集中到 `config.py`（或对应语言的项目配置模块），通过环境变量控制。`.env.example` 同步更新。新增配置项约 30 个。

**检查项**：
- [ ] 所有魔法数字（超时、阈值、默认值）是否都提取到配置类？
- [ ] 默认值在无 `.env` 时也能启动？

### 2. 测试数据必须真实可连

**问题**：seed 数据写了不存在的数据库名，导致数据源连接测试全部失败。看起来"功能正常"，但实际全是 CONNECTION_FAILED。

**做法**：所有 seed 数据必须指向真实可连的数据库。测试前先用 `SHOW DATABASES` 确认可用库。seed 后逐个执行 `SELECT 1` 验证连通性。

### 3. JWT token 必须包含所有鉴权需要的字段

**问题**：JWT 里没有 `role` 字段，导致 admin 接口永远 403。

**做法**：登录创建 token 时，把所有 downstream 鉴权需要的字段都写进去：`user_id`、`email`、`tenant_id`、`role`。刷新 token 时同样。

### 4. 异步 ORM 的 merge vs add

**问题**：SQLAlchemy async session 的 `merge()` 返回 coroutine 需要 await，没 await 导致数据没写入。

**做法**：批量插入用 `session.add()` + `commit()`。需要 upsert 用 `await session.merge()`。

### 5. 测试隔离：单元测试不碰真实数据库

**做法**：测试配置里在导入 app 之前覆盖 `DATABASE_URL` 为 SQLite in-memory。每个测试自动建表/删表。

### 6. API 冒烟测试覆盖所有模块

不能只看 health 和 login。每个模块都要测：
- auth: 注册、登录、刷新、锁定拒绝、未验证拒绝
- datasources: 列表、创建、测试连接、删除
- queries: 列表、保存、重跑
- feedback: 列表、提交
- audit: admin 可访问、非 admin 拒绝
- export: CSV 导出
- conversations: 列表

### 7. 每次变更后的测试流程

1. 全量单元测试通过（确认 N passed, 0 failed）
2. 启动后端确认无启动报错
3. 逐个测试关键 API（至少 login、list、POST query）
4. 验证数据库行数与预期一致
5. 数据源连接测试返回 success

### 8. seed 脚本是可复用的基础设施

**做法**：`seed.py` 必须支持重复运行（truncate + insert），每次得到一致数据。UUID 固定（不用随机生成），方便测试引用。

### 9. 前端 500 排查清单

当前端说"所有接口都 500"时：
1. 先 `curl health` 确认后端活着
2. 检查前端 proxy target 是否指向正确端口
3. 确认没有多个进程占着端口（`lsof -ti :PORT`）
4. 看后端日志里有没有实际收到请求
5. 检查 CORS 配置是否允许前端域名

## 第五章：7 条核心原则

1. **规划的目标不是预测正确，而是排除失败。**
2. **每个"显性需求"背后都藏着一个"隐性基础设施需求"，比例约 1:1。**
3. **借别人的失败比自己踩坑 ROI 高 100 倍。**
4. **文档一致性不是洁癖，是信任的基础。**
5. **任何不可精确测量的目标都是愿望，不是规划。**
6. **自己永远看不到自己的盲点——必须被"不知道你在想什么"的人审查。**
7. **"不做"什么定义了产品的边界。**
